一个 763B 参数的模型，Q8_0 量化后约 473 GiB。跑它的那台 MacBook Pro 只有 48 GB 统一内存，连零头都装不满。InferSSD 把路由专家留在 SSD 上，每个 token 只把被选中的那几块读进来，预填充做到 28.766 token/s、解码 2.874 token/s——同一台机器、同一份 GGUF，比 llama.cpp 快 3.29 倍。

反直觉的地方不在"能跑"。llama.cpp 早就能跑装不下的模型：文件映射进虚拟地址空间，缺页时交给操作系统去取。真正扎眼的是，一个绕过操作系统、自己记账读盘的引擎，在同一份权重上把缺页机制甩开了。

---

## 项目背景：mmap 已经把地板垫到了 0.87 token/s

DeepSeek-V4.1-Flash-1017 总参数 763B，每 token 只激活 8–16B。稀疏激活是 MoE（混合专家）的全部意义：路由器在几百个专家里挑几个，剩下的从不参与这次计算。但常规的本机推理不用这个差值——它要求全部权重先在内存里排好队，才肯吐第一个字。

llama.cpp 的 `mmap` 是这个困局的第一个答案，也是所有人的起点。模型按页映射，缺哪页读哪页，不占常驻内存。跑得起来，但慢得离谱：在这台 M5 Max 上，它处理 4,104 token 的提示词花了 692 秒，生成 256 个 token 再花 290 秒，解码停在 0.873 token/s。

原因写在机制里。操作系统的页缓存用近似 LRU 管理 4 KiB 页面，它不知道下一个 token 会选哪个专家，也没有能力把同一次前向里分散的读合并成大块顺序读。模型文件有 470 GB，页缓存的每一次决策都像在黑箱里猜。

Colibri 走另一条路：按专家粒度组织缓存，纯 CPU，8 线程、每层驻留 8 个专家（约 5.60 GiB）。它换来了确定性，也换来了更差的成绩——同一个请求跑了 1 小时 46 分，解码 0.437 token/s。

问题于是被拆成两半：**能不能预知下一次读什么，以及能不能把读做大。**

## 核心功能

### 1. 专家索引：把 GGUF 当目录，不改一个字节

`store/` 这一层只解析 GGUF 头部，记录每个专家张量在分片里的字节区间，不复制模型载荷。可选的做法是生成一份 v1 expert pack：按层和专家重新排列切片，4 KiB 对齐，量化字节原样搬运——打包只做拷贝，不做二次量化。

对齐这件事值得多说一句。NVMe 的最小读写单位是 4 KiB，一次未对齐的逻辑读会被拆成两次设备读，带宽直接腰斩。专家切片本身就是矩阵块，尺寸天然不规整，4 KiB 对齐等于把这个损耗提前消掉。

代价是绑定关系：v1 格式里没有 checkpoint 指纹字段，pack 必须和它的源模型成对保管，换一个 checkpoint 就得重建。

### 2. 每个系统一个 read ring，不从页缓存借道

Linux 用 `io_uring`，Windows 用 `IoRing`，macOS 用常驻 reader 线程配 `F_NOCACHE`。三套实现共享同一层接口，`engine/ggml/src/ggml-ssd/io/` 下一个平台一份文件。

绕过页缓存意味着放弃操作系统的免费预读和跨进程共享，换来的是每一页的进出都由自己的成本模型决定。这是整个设计的地基：如果读还经过页缓存，"知道该读什么"就没有意义——内核仍然可以按自己的 LRU 把你刚预取的专家挤出去。

### 3. 缓存按预算租借，不是一个固定的池

`host/` 里那套实现管三件事：载荷区、预算准入、租约。分配之前先向进程仲裁器申请；申请不下来不是报错，而是让专家缓存先吐空间——缓存的回收器注册在 context 的 host client 上，所以连 CPU 后端的工作缓冲区也能靠它腾地方。Linux 上预算来自 cgroup 约束，macOS 和 Windows 用进程包络。

基准里 Mac 用 8 GiB 的 LFU 缓存，`cache_policy` 默认是 `window`，支持按层设配额、按优先级分配。之所以做成可调，是因为不同机器的瓶颈不同：48 GB 的笔记本该多给缓存，8 GB 内存加 16 GB 显存的台式机该多给显存。

### 4. 用实测成本表决定专家在哪算

每个推理 pass 运行的时候，sink 顺手量下每条路径的耗时，写进一张成本表；下一次放置决策读这张表，判断这个专家进 CPU 还是进 CUDA 的显存层，以及要不要预取。新形状的第一次执行不进拟合——没见过的权重格式组合、几何、激活类型、专家行数都排除在稳态之外，避免一次冷启动把表带偏。

放置逻辑集中在 `place/runtime-policy.h`，它不持有 sink、设备或文件句柄。CPU 和 CUDA 两个执行器共用同一套成本算术和选择阈值，所以"在哪算"的答案不会因为后端不同而漂移。

### 5. GPU lane：共享内存的 GPU 只在预填充时出手

Metal 和 Vulkan 没有 CUDA 那条显存缓存层，但它们共享 host memory。InferSSD 给这类 GPU 开了一条 `gpu/graph-lane.cpp`：预填充时把这一轮里"重"的专家整条图交给 GPU——一个专家被很多 token 用到时，权重读一次就喂给所有行，比 CPU 划算得多。

解码时不行。每个专家只有一行，传输开销盖不住收益，所以解码留在 CPU。lane 跨层不留状态，host 预算也不变。这条设计承认了一件常被忽略的事：同一个专家在预填充和解码阶段的性价比完全不同。

### 6. 下单 470 GB 之前，先测你的盘

`inferssd profile --model <路径>` 用一个 4 GiB 临时文件测盘，给出各模型在本机的解码速度估算，测完删掉。

这并非装饰功能。首次运行要下约 470 GiB，Muse 那档更大；下载前先知道盘能不能扛，比下完发现只有 0.2 token/s 便宜太多。

## 技术亮点

### 1. 把"缺页"换成"计划"，代价是支持面

llama.cpp 把放置权交给内核，InferSSD 把它收回进程。收益可以量化：同一个 4,104 token 请求、同一份 GGUF、同一台机器，总时长从 982 秒降到 347 秒，预填充从 692 秒降到 219 秒。

成本同样明确——每个模型都要有 adapter。`engine/src/ssd/model-adapter.h` 校验专家布局、量化位宽之间的关系、激活与归一化要求，全部通过之后才允许 MoE 桥建立执行节点。目前过审的只有五个档位：DeepSeek-V4.1-Flash、Muse-Spark-Open、Qwen3.6-35B-A3B、Qwen3.8 Flash Next，以及走普通内存路径的 Gemma4 E4B。

这是典型的取舍：**通用性换确定性**。想加新模型，得读懂它的路由结构和量化方案，不能靠试。

### 2. 线程数由带宽决定，不由核数决定

解码阶段的线程池不是"开满"。启动时它会找出"刚好能把专家权重喂到最佳实测速率"的最少线程数——再往上加只是加等待，内存带宽已经饱和。

更细的一层在 token 之间：它测量被别的线程（GPU 后端、读线程、其他进程）占走的 CPU，下一次就少开这么多。执行器之间不加锁，0 号线程用一个原子字发布阶段，其余线程轮询 3 ms 后挂到操作系统的 wait-on-address 原语上，一次唤醒就能通知全员。

这段代码不好看，但它解释了差距从哪来：CPU、带宽、盘被当成一份预算一起分配，而不是各管一段。

### 3. 边界写成脚本，能跑

`scripts/inferssd/check-layering.py` 检查依赖方向：核心只依赖 ggml-base 和平台设施，CPU 执行器不链 CUDA，CUDA 执行器不链 CPU。三套操作系统的 ring、两种 GPU 后端、一个 62 文件 502 KB 的独立模块（`ggml-ssd/`），靠这条纪律维持可移植性。

`host/expert-cache.h` 一个文件 1,491 行，注释密度高得不像 C++ 项目——每个决策点都写清了为什么。

## 适用人群

- **想在本机跑 700B 级开源 MoE 的个人研究者**：机器内存和显存都远小于权重规模时才有意义。2.5–7 token/s 适合评测、批处理、长任务，不适合对话。
- **数据不能出内网的团队**：`inferssd serve` 提供一个 OpenAI 兼容端点，Claude Code、OpenCode 这类客户端能直接指过去，本地模型就变成了可替换的后端。
- **做推理系统的工程师**：一份能读的参考实现——成本表、预取、read ring、租约，每块都独立成目录，可以只抄一节。
- **暂时不适合**：需要交互速度的对话产品；只用 dense 模型的场景，每个 token 都要大部分权重，收益为零；把 Windows 当主力机的开发者。

## 快速上手

```sh
# Apple Silicon macOS，或带 NVIDIA GPU 的 Linux
curl -fsSL https://github.com/wici-ai/inferssd/releases/latest/download/install.sh | sh

# 先测盘，再决定要不要下 470 GiB
inferssd profile --model /path/on/ssd

# 终端聊天，或起服务（http://127.0.0.1:8080）
inferssd cli   -hf mrfakename/DeepSeek-V4.1-Flash-1017-GGUF
inferssd serve -hf mrfakename/DeepSeek-V4.1-Flash-1017-GGUF
```

前置依赖：Git、Python 3.9+、C/C++ 编译器。macOS 还要 Xcode Command Line Tools，Linux 还要 CUDA toolkit、liburing 头文件和带 cgroup v2 的 systemd。安装器不用 sudo，源码编译 2–12 分钟。

几个坑先记下：DeepSeek 档最低 16 GB 内存、约 520 GB 空闲盘；容器和没开 systemd 的 WSL 会在启动前被拒；`serve` 默认只听回环，加 `--host 0.0.0.0` 之后**没有鉴权**，同网段谁都能用；Windows 有预编译包，但状态仍标为进行中。

## 对比分析

| 维度 | InferSSD | llama.cpp（mmap） | Colibri |
|---|---|---|---|
| 运行形态 | 独立引擎，内含 llama.cpp 快照 | 单文件 + 内存映射 | 研究实现，纯 CPU 专家缓存 |
| 装不下的模型 | 设计目标 | 能跑，速度崩塌 | 能跑，更慢 |
| Mac 48 GB · DeepSeek 预填充 | **28.766** tok/s | 5.929 | 0.708 |
| Mac 48 GB · DeepSeek 解码 | **2.874** tok/s | 0.873 | 0.437 |
| RTX 5090 · DeepSeek 解码 | **7.270** tok/s | 0.867 | 1.878 |
| 256 GB Mac Studio 解码（第三方） | 3.45 tok/s | **10.95** | 未测 |
| 局限 / 风险 | 模型白名单窄、磨损未知、单次跑分 | 大模型上不可用 | 预填充极慢 |

表里的数字不是同一组实验。中间三行的速率由项目团队在自己的测试机上测得（项目自述），条件是 4K 提示词、256 token 输出、取第 129–256 token 窗口，同硬件同 GGUF；Colibri 那列跑的是混合精度 safetensors 加 CPU 后端，属于配置对配置，不是严格对等。最后一行来自第三方在 256 GB Mac Studio 上的复测，模型同为 473 GiB 的 DeepSeek V4.1 Flash。两组都成立，指向的结论不同：**谁快，取决于内存装不装得下模型。**

## 局限

最硬的一条：**大内存机器上它输三倍。** Novel Cognition 在 256 GB Mac Studio 上用同一份权重、同一套基准脚本跑了一夜，llama.cpp 解码 10.95 token/s，InferSSD 最好设置 3.45 token/s。交叉点大约在 130–150 个输出 token 之后——再长，llama.cpp 就反超。原因是那条路径上操作系统有 223 GiB 文件缓存可用，mmap 退化成内存访问；而 InferSSD 仍在按 0.37 GB/token 的速率读盘，llama.cpp 是 0.023 GB/token。它解决的问题只在"内存装不下"时存在。

第二条是测量本身的成色。4K 那一档每次结果只跑一遍；Mac 上的运行是冷进程，但没清系统文件缓存，所以不是受控的冷缓存测量。跨引擎对比是完整配置对完整配置，拆不出单个优化的贡献。这些限制写在基准方法文档里，态度诚实，但不改变结论的置信度。

第三条是模型不等价。Mac 上加载的 GGUF 报 748.49B 参数、1,046 个张量，官方完整 checkpoint 是 763B——转换掉了视觉和 MTP 分支，量化也不是无损。吞吐对比没有包含答案质量，两边都没做正确性评测。

第四条是 SSD 磨损。按 DGX Spark 的日志外推一个密集使用场景：每天 8 小时、50% 占空比（等于 4 小时连续读），约 85 TB 主机读取/天。这只是用预填充阶段的专家拷贝量做的代理估算，不是实测块设备总量。内部刷新写入按 DEAR 实验的比例（3% / 8% / 27.3%）折算，而那是 SATA 盘 4 KiB 随机读的数字，不能直接套到对齐的大块 NVMe 读上。持续跑会不会烤盘、笔记本散热能不能撑住一小时以上的任务，官方未说明，第三方也没有测。

第五条是绝对速度。0.219 token/s（Muse 在 RTX 5060 Ti 上）基本等于不可用，7.27 token/s 是四台机器里的最好成绩。能跑和能用是两件事，宣传语容易把这两件事混起来。

第六条是工程成熟度。五个模型档位，加新模型要写 adapter；Windows 状态未定，两个未关闭的 issue 分别是 Vulkan/AMD 上 DeepSeek 输出不连贯（#284）和 Windows 上的 `ggml-cpu/ops.cpp:5260` 断言失败（#272）；贡献者只有个位数，第一个版本发布于 10 月 30 日。

还有一条容易被忽略：社区讨论很薄。Hacker News 上两个帖子，峰值 1 分和 3 分，评论都是 0；中文圈能查到的多是同一段通稿的转载。这个项目的传播靠的是厂商的产品视频，不是开发者的口碑，判断它的时候要把这层折价算进去。

## 写在最后

两件事值得记住。

第一，**它把"能不能在本机跑"从容量问题改成了带宽问题**，而且证明这件事有工程解：不等更强的硬件，而是把 I/O、缓存、放置三件事放进同一个成本模型里一起算。那 636 秒的差距来自几百行调度代码，不来自新芯片。

第二，**它顺手划出了自己的边界**。同一份权重，48 GB 笔记本上快 3.29 倍，256 GB 工作站上慢 3 倍。这不矛盾，是同一个机制在不同内存预算下的两种结果。换个说法：如果你机器的页缓存已经装得下模型，这个项目对你没有价值。

行动建议只有一条：先跑 `inferssd profile`，让盘和内存自己说话，别急着下 470 GiB。48 GB 级、想跑 700B 级 MoE 的机器，值得花两小时装一次；256 GB 级工作站，继续用 llama.cpp。把它当批处理和评测引擎，不要当聊天引擎。
