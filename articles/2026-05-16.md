# RAG-Anything：港大开源多模态RAG框架，统一处理文本/图像/表格/公式

> 现代文档早已不是纯文本——论文里有实验图表和数学公式，财报里有统计表格和趋势图，技术文档里有架构图和代码片段。传统RAG系统只能处理文本，遇到这些多模态内容就束手无策。香港大学黄超教授团队在 LightRAG 基础上，开源了 **RAG-Anything**，用统一框架把多模态内容全部纳入RAG流水线。

---

## 项目背景

RAG（检索增强生成）技术在过去两年高速发展，从最初简单的向量检索，进化到知识图谱增强（GraphRAG、LightRAG）。但现有方案有一个共同局限：**只处理文本**。

现实中的文档远不止文字。一篇学术论文包含：摘要（文本）、实验图表（图像）、数据表格、数学公式；一份财务报告包含：分析文字、趋势折线图、财务数据表。传统RAG系统的做法是把图像/表格做成OCR，强行转成文本——这丢失了视觉布局、颜色编码、空间关系等关键信息。

**RAG-Anything 的核心思路**：把文档中的文本、图像、表格、公式统一建模为知识图谱中的实体和关系，用多模态方式做检索和问答。该项目由香港大学数据科学团队（HKUDS）开发，2025年6月首次开源，截至2026年5月已收获 **20,241 Stars**，并有对应的 arXiv 论文（ID: 2510.12323）支撑。

## 核心功能

### 1. 统一多模态文档解析
支持 **10+ 种文档格式**的原生解析：PDF、Word（.doc/.docx）、PowerPoint（.ppt/.pptx）、Excel（.xls/.xlsx）、图像（.jpg/.png/.tiff/.webp）、Markdown、纯文本、HTML。
- 使用 **MinerU** 作为默认解析后端，可切换为 **Docling** 或 **PaddleOCR**
- 解析输出标准化的 `content_list` 结构，每条记录带类型标签（`text`/`image`/`table`/`equation`）

### 2. 多模态内容智能分析
针对不同类型内容，RAG-Anything 内置三个专用分析器：
- **图像分析器**：调用视觉大模型（VLM）生成高质量图像描述，提取空间关系和视觉要素
- **表格分析器**：深度理解表格层次结构，自动识别表头关系、数据类型和逻辑联系，提炼数据趋势
- **公式分析器**：精确识别 LaTeX 格式数学表达式，分析变量含义和公式结构

### 3. 跨模态知识图谱构建
这是 RAG-Anything 最核心的创新。系统将文本段落、图像描述、表格数据、公式全部抽象为知识实体，并自动构建跨模态的语义关系图谱。

| 实体类型 | 示例 | 关系类型 |
|---------|------|---------|
| 文本段落 | "实验方法描述" | 同文档引用、语义相似 |
| 图像 | 图3：准确率对比图 | 被引用于段落X、说明Y |
| 表格 | 表2：不同方法性能对比 | 数据支撑结论Z |
| 公式 | Eq.5：损失函数定义 | 被应用于段落W |

### 4. 双层次混合检索
RAG-Anything 支持两种检索粒度，并可将两者结果融合：
- **细粒度关键词检索**：精准定位具体实体（某个图表、某条公式）
- **概念级语义检索**：把握主题脉络（"这个文档关于什么研究方向"）

检索策略同时利用知识图谱的结构化关系和向量数据库的语义相似度，比纯向量检索更精准。

### 5. 多模态问答（VLM增强）
用户提问可以涉及非文本内容：
> "文档中的图3展示了什么趋势？"  
> "表2中哪个方法性能最好？"  
> "公式5的物理意义是什么？"

系统自动识别问题涉及的多模态元素，调用对应的分析器，并可选启用 VLM 增强，生成准确回答。

### 6. 灵活的输入模式
- **端到端模式**：直接丢进去一个 PDF/PPT，全自动处理
- **精细控制模式**：手动构造 `content_list`，精确控制每个内容块的处理方式
- **增量更新**：基于 Merkle 树检测文件变更，只重新索引修改过的部分

## 技术亮点

### 亮点一：基于 LightRAG 的三层架构
RAG-Anything 并不是从零重构，而是**组合式架构**：在 LightRAG（负责知识图谱+向量存储）之上，增加了多模态处理层。

```
┌─────────────────────────────────────────────┐
│         RAG-Anything 处理层                │
│  (文档解析 + 多模态分析 + 内容注入)          │
├─────────────────────────────────────────────┤
│            LightRAG 核心层                  │
│   (知识图谱构建 + 向量存储 + 检索排序)       │
├─────────────────────────────────────────────┤
│            存储层                           │
│   (Neo4j / Milvus / Chroma 等可插拔)      │
└─────────────────────────────────────────────┘
```

这种架构设计意味着：如果你已经部署了 LightRAG，可以**无缝升级**到多模态版本，复用已有的知识图谱和向量存储。

### 亮点二：智能分块与上下文保留
传统 RAG 的固定长度分块（如每500字一切）会切断表格、公式的完整性。RAG-Anything 的做法是：
1. 用 MinerU/Docling 做**结构感知分块**，按文档的逻辑结构（段落、章节、列表）切分
2. 对多模态内容，自动提取**周围文本上下文**（可配置上下文页数和 token 上限），保证检索时能看到"这张图伴随着什么文字说明"

### 亮点三：可扩展的插件化架构
系统设计充分考虑到不同领域的扩展需求：
- **自定义模态处理器**：继承 `BaseModalProcessor`，只需实现 `process_multimodal_content()` 方法，就能支持新的内容类型（如化学结构式、乐谱符号）
- **自定义解析器**：继承 `Parser` 基类，接入新的文档解析引擎（如 Tesseract OCR）
- **直接内容注入**：不需要文件，直接往系统里插入构造好的 `content_list`

## 快速上手

### 安装

```bash
# 前提：Python 3.10+
pip install raganything

# 或使用 uv（推荐，更快）
uv pip install raganything
```

### 最小可运行示例

```python
import asyncio
from raganything import RAGAnything, RAGAnythingConfig

# 1. 配置
config = RAGAnythingConfig(
    working_dir="./my_rag_data",
    parser="mineru",              # 解析后端：mineru / docling
    enable_image_processing=True,  # 启用图像处理器
    enable_table_processing=True,  # 启用表格处理器
    enable_equation_processing=True,  # 启用公式处理器
)

# 2. 初始化（需要传入 LLM 和 Embedding 函数）
from lightrag import LightRAG

rag = RAGAnything(
    config=config,
    llm_model_func=your_llm_func,        # 任意兼容 LightRAG 的 LLM 函数
    embedding_func=your_embedding_func,    # 任意兼容 LightRAG 的 Embedding 函数
    vision_model_func=your_vlm_func,       # 可选，用于图像理解
)

# 3. 处理文档
asyncio.run(rag.process_document_complete("paper.pdf"))

# 4. 提问（支持多模态）
answer = asyncio.run(
    rag.aquery("图3展示了哪些方法的性能对比？", use_vlm=True)
)
print(answer)
```

### 性能特点（基于架构分析）

虽然官方未发布标准基准测试数据，但从架构设计可以推导出以下性能特点：

- **索引耗时**：首次处理复杂PDF时，MinerU解析 + 多模态分析是主要耗时步骤。对于100页学术论文，预计解析耗时2-5分钟（取决于VLM调用速度）
- **检索精度**：跨模态图谱检索比纯向量检索更精准，特别是对"某张图说明了什么"这类问题
- **存储开销**：多模态实体的向量表示比纯文本多约30-50%（需要存储图像/表格的嵌入），但仍在可接受范围
- **Token消耗**：VLM增强问答会比纯文本问答消耗更多token（图像描述+上下文），但比把整个文档塞进上下文要高效得多
