一个 0.6B 的小模型，被塞进了三个总共不到 72KB 的二进制里：一个 14KB 的 Linux 推理引擎，一个 24KB 不需要操作系统的裸机聊天系统，一个 32KB 从零训练的 GPT 训练器。全部代码是手写 x86-64 NASM 汇编，零 C、零 libc、零运行时依赖。它两天拿了 1,800+ 星，不是因为能用，而是因为它把一个问题拍在了桌上：跑一个大模型，到底需要多少层软件？

项目背景：推理栈下面还压着多少东西

用 llama.cpp 在笔记本上跑一个本地模型，已是极简路线的代表。但它仍是一个数 MB 的通用引擎，底下垫着内核、驱动、C 运行时和动态链接器。从按下电源到吐出第一个 token，中间隔着 BIOS、引导程序、内核初始化、libc 装载、mmap、线程调度——每一层都在消耗内存和启动时间，只是这些开销通常被模型本身的大小掩盖了。

对 7B、70B 的模型来说，这层开销可以忽略；但对 0.6B 级别的小模型，系统软件的占比开始变得刺眼。粗算一笔账：一个 614 MiB 的量化模型跑在一台 8GB 内存机器上，内核、libc、运行时连同各自缓存的页，加起来可能吃掉一两个 GB——折算下来，跑模型之前系统已经先收了一次「过路费」。Hacker News 上有人算过类似的账：在数据中心托管大模型时，OS 层几乎不花什么资源，所以没人有动力砍它；反过来，小模型场景里这层开销就成了主要成本之一。

另一个背景是「击败 llama.cpp」近来成了社区高频动作。HN 评论区有人泼冷水：llama.cpp 是为任意硬件、任意模型设计的通用引擎，针对单一模型手写优化引擎超越它是意料之中，甚至有人让大模型现场生成推理引擎来刷纪录。这个项目有意思的地方在于，它没有走「AI 生成代码」的捷径——17,252 行汇编要一行行对得上 PyTorch 的数值，混不了水。

这条极简谱系上此前有过别的尝试：把 RISC-V CPU 编译进模型权重的 Qwenputer（本账号 11-20 期写过），走的是「让模型自己算自己」的路线。llm.asm 反过来，是让一台什么都没有的机器，直接变成推理机。

核心功能

1. asm-llm：14,712 字节的推理引擎

静态链接的 Linux ELF，readelf -d 看不到任何动态段。完整实现 Qwen3-0.6B 的 28 层前向：16 个查询头配 8 个 KV 头的 GQA、RoPE 之前的 QK-Norm、SwiGLU 前馈、绑定词嵌入，外加多轮对话的 KV-cache，支持 --chat 进入交互 REPL，/clear 清上下文、/think 切思维模式。BPE 分词器也是汇编——一张 524,288 槽的斐波那契哈希 merge 表，与 HuggingFace tokenizer 逐 token 对齐。权重经离线 Python 脚本一次性导出为自定义 .asmbin 格式（613.66 MiB，比 BF16 safetensors 的 1.40 GiB 省一半多），每行 64 字节对齐，运行时 mmap 零拷贝加载，此后 Python 不再参与。

2. asm-llm-os：24,252 字节的裸机聊天系统

同一个汇编核，换一个编译开关，Linux syscall 被替换为物理内存分配、APIC 自旋屏障和 VGA/PS-2/串口驱动，产出一个不需要任何操作系统的内核。Multiboot 引导 → 四级分页 → 长模式 → AVX2/FMA/F16C 检测 → ACPI MADT 枚举多核 → INIT-SIPI-SIPI 唤醒 16 个核，然后直接进聊天界面。实测开机 74–94 毫秒，磁盘占用 0 GB——权重作为引导模块跟内核一起加载。VGA 文本模式里直接和多轮 KV-cache 聊天，是这个项目最出圈的画面。

make os FAST_Q8=1
make os-run MODEL=models/qwen3-0.6b-q8_0.asmbin SMP=16

3. asm-gpt-train：32KB 从零训练器

不只推理，连训练都是汇编。寄存器分块的 6x16 AVX2+FMA SGEMM，完整解析式反向传播，解耦 AdamW，外加一个 80x24 终端里用盲文字符实时画损失曲线的 TUI。在 TinyShakespeare 上训一个 2.68M 参数的 Mini-GPT，验证损失从 4.19 降到 1.51 用时约 4 分钟，训练吞吐 27,662 token/s。反向传播的梯度与 PyTorch CPU 逐张量对拍：21 个参数张量的余弦相似度全部为 1.0000000000，最大绝对误差 3.35e-8。

4. 三个项目共享一个汇编核

math.asm（expf、sincosf、RMSNorm、Softmax 的 SIMD 实现）、matmul.asm、tokenizer.asm、transformer.asm 四个文件共 3,857 行，被三个二进制复用。裸机版只是把内存分配和线程同步的底层实现换掉——Linux 的 mmap、clone、write 换成物理 Multiboot 模块、APIC 自旋屏障和 VGA 驱动，上面的 transformer 前向一行不改。这种「一份核心、三种形态」的结构，让三个项目互相印证：如果裸机版输出和 Linux 版字节级一致，说明两边都没写错。

技术亮点

1. 快路径是 INT8×INT8 而不是 FP32

默认的 FAST_Q8=1 路径用 AVX2 的 vpmaddubsw/vpmaddwd 做 INT8×INT8 点积，块 scale 用 F16C 指令转 FP16，配合单调预取和按头切分的并行 GQA 注意力。结果是 40 线程解码 126.8 tok/s（峰值），比 llama.cpp CPU 跑同一份 Q8_0 权重快 18%–36%（1 到 40 线程区间），且 64 个贪心采样 token 与 PyTorch FP32 全部一致、余弦相似度 0.99965（项目自述，基准机为 AMD EPYC 7642）。想看精确数值可以切回 FAST_Q8=0 的 FP32 路径，与 Python Q8_0 参考实现余弦 1.0。

2. 裸机版为什么反而更快

裸机内核比 Linux 版再快约 10%，来源是 2 MiB 大页恒等映射——没有页表切换和 TLB 压力，权重常驻物理内存。多核同步靠 APIC 自旋屏障而不是 futex，省掉内核态切换。这些收益在通用推理引擎里拿不到，因为它们依赖「没有 OS」这个前提本身。

3. 确定性作为工程约束

1 线程到 40 线程输出 bit-exact，1 到 32 个 vCPU 的裸机版输出字节级一致。线程池是汇编写的这一条值得单独说：threads.asm 用裸 clone() 系统调用起线程，同步用自旋加 futex 的混合策略——短任务自旋等待，长任务才陷进内核挂起。这套东西在 C 里是 pthread 的事，在这里只有 439 行。仓库自带三个对拍脚本（NumPy/PyTorch 参考实现、SMP 确定性检查、AdamW 轨迹校验），数值验证不是附带品，而是设计目标。对一个全手写汇编的项目，这是唯一能让人相信「没写错」的方式。

适用人群

  • 推理引擎工程师：想看清 transformer 每一层在硬件上真实长什么样，这个仓库是一份带数值对照的解剖标本，RMSNorm、RoPE、Softmax 的 SIMD 写法可直接参考。
  • osdev 与系统程序员：Multiboot 到 SMP 唤醒的完整链路（412 行 boot.asm）是难得的现代长模式启动教学样本。
  • 边缘与嵌入式探索者：0 GB 磁盘、74 毫秒启动的「token 家电」思路，对离线专用设备有参考价值。
  • 教学者：从矩阵乘到反向传播到 AdamW 全在一门汇编语言里，适合做「LLM 没有魔法」的实证教材。

快速上手

前置条件：x86-64 CPU 带 AVX2 + FMA + F16C（Intel Haswell / AMD Excavator，2013 年起），Linux 环境，nasm 与 binutils。

sudo apt install nasm binutils
git clone https://github.com/alesha-pro/llm.asm.git
cd llm.asm && make all

# 导出权重（一次性，需 python3 + numpy）
python3 scripts/export_weights.py --model-dir models/qwen3-0.6b-bf16 \
    --out models/qwen3-0.6b-q8_0.asmbin --scale-dtype fp16

make inference FAST_Q8=1
./build/asm-llm -m models/qwen3-0.6b-q8_0.asmbin --chat -t 16

常见的坑：权重需要先从 HuggingFace 下载 BF16 版再导出，仓库不带权重文件；虚拟机里跑裸机 OS 需要开启嵌套虚拟化（KVM）才有完整性能；无 AVX2 的老 CPU 直接编译不过。

它的对手不是 llama.cpp——后者是给所有人的通用引擎，前者是一次极限条件下的工程证明。真正被改变的是参照系：原来「跑一个 LLM 所需的全部系统软件」可以压到几十 KB，而压掉这些层之后，输出可以和 PyTorch 一模一样。

局限

  1. 所有性能数字自报。基准来自作者单台 EPYC 7642、34 个提示 token / 64 个生成 token 的短基准，截至发稿无独立第三方复现。newruntime.com 的分析指出对比本身不完全对等：llama.cpp 的预填充用批量 GEMM，llm.asm 逐 token 跑 GEMV，两者测的不是同一种负载。
  2. 模型上限锁死。只有 0.6B 一个模型的能力档位，没有 harness 的裸聊天实用价值有限——HN 首页高赞评论称之为「罐装大脑」，认为更多是概念演示；也有评论反驳 harness 本来就该跑在别的机器上，推理端做成「token 家电」反而是干净的架构。
  3. 平台绑定 x86-64。AVX2/FMA/F16C 三件套缺一不可，也就是说 2013 年之前的机器直接出局，ARM 设备（树莓派、手机、大多数云端 ARM 实例）完全无缘；裸机版也没有网络栈，远程调用需要自己搭，等于只能本地或同机串口交互。
  4. 单人单日项目。贡献者仅作者一人，仓库 3 次提交、无 release 无 tag，发布仅两天（截至 2026-11-27），长期维护与模型扩展意愿未知。
  5. 安全叙事是双刃剑。没有 syscall 确实消掉一类攻击面，有评论认为这对长期联网部署反而是优点——没有系统更新可以搞坏它，行为完全可预测。但 HN 评论区也有人指出：一个能裸跑在任意 x86 机器上的模型二进制，本身可以成为新的攻击载体，这两面性在仓库里都没有展开讨论。
  6. 中文支持未经说明。分词器对齐的是 HuggingFace 原版 tokenizer，理论上支持多语言，但项目未给出中文对话质量的任何测试，官方未说明。

写在最后

这个项目真正值得记住的不是「比 llama.cpp 快两成」，而是它把推理栈的每一层都摊开在了桌面上：数学核、矩阵乘、分词器、线程池、内核、驱动，各自值多少字节、值多少毫秒，第一次有了逐项答案。当模型越小、部署越散，这些答案就越值钱。

对读者的建议：想搞懂 LLM 推理的，去读 shared/ 目录那 3,857 行，比任何教程都诚实；想在边缘设备上做离线小模型的，把它当架构参考而不是生产依赖；只想围观的，去裸机版开一次机——74 毫秒等来一个会说话的操作系统，值得。
