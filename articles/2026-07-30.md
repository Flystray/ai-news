## 项目背景：Ollama 的"够用"，和 M 系芯片被浪费的带宽

在 Mac 上跑本地大模型，Ollama 几乎是默认答案：一条命令启动、模型库全、跨平台。但它的底层是 llama.cpp——一个为"CPU + 独立显卡"异构体系设计的引擎。而 Apple M 系芯片是**统一内存架构（UMA）**：CPU 和 GPU 共享同一块内存池，本不需要任何跨总线数据拷贝。用 llama.cpp 的思路跑 M 系芯片，等于给跑车挂了拖拉机的变速箱。

Rapid-MLX 的答案是彻底放弃 llama.cpp：**纯 MLX 内核，无回退、无 Metal 垫片**。MLX 是 Apple 官方的机器学习框架，为 UMA 原生设计，模型权重直接驻留在共享内存池中做零拷贝张量运算。在这个地基上，项目又叠加了连续批处理（continuous batching）、量化 KV 缓存（int4/int8 + TurboQuant K8V4 编解码器）、radix 树提示缓存 + DeltaNet RNN 状态快照、DFlash 块扩散投机解码等一整套推理优化——很多是 vLLM 级别的服务端技术，第一次被系统性搬到 Mac 本地。

有个耐人寻味的细节：代码包名至今仍叫 `vllm_mlx`——这个项目的野心从名字就能看出来：**做 Apple Silicon 上的 vLLM**。

## 核心功能

### 1. 极速推理：实测数据全公开

官方基准（M3 Ultra，Qwen3.5-9B）：Rapid-MLX 108 tok/s，Ollama 46 tok/s，上游 mlx-lm 62 tok/s——**比 Ollama 快 2.3 倍，比 Apple 自家 mlx-lm 快 1.7 倍**。在 GPT-OSS-20B 上优势拉大到 4.2 倍（127 vs 79 tok/s）。16GB MacBook Air 跑 Qwen3.5-4B 可达 160 tok/s（仅占 2.4GB 内存）——比人类阅读速度还快。项目还提供 `rapid-mlx bench --submit` 标准化测试，可把你的机器数据提交到公开天梯榜。

### 2. 提示缓存：多轮对话"免费重启"

对交互式编码助手来说，首字延迟比吞吐量更影响体验。Rapid-MLX 为 Transformer 模型维护 KV 缓存，为 Qwen3.5 这类 RNN-Attention 混合架构额外记录 **DeltaNet 状态快照**：Devstral-24B 的 TTFT 从冷启动 0.38 秒降到热启动 0.13 秒（2.9 倍）；Qwen3-Coder-Next 6bit 从 0.66 秒降到 0.16 秒（4.3 倍）；Kimi-Linear-48B 缓存命中时低至 **0.08 秒**——几乎无感。

### 3. 17 种工具调用解析器 + 11 个 Agent CLI 实测认证

工具调用是 Coding Agent 的命脉，但每家模型的 function calling 格式都不一样（Qwen、Hermes、GLM、MiniMax……）。Rapid-MLX 内置 17 种模型专属解析器，并按等级维护 Agent 兼容矩阵：**Tier-1（Claude Code、Codex CLI、Hermes、Aider）每个版本都做端到端重验**；Tier-2 覆盖 OpenCode、GitHub Copilot、Kimi Code 等 7 个。工具调用如果以纯文本形式"降级到达"，引擎还能自动恢复解析。

### 4. OpenAI + Anthropic 双协议，一个 URL 接入全生态

不只兼容 `/v1/chat/completions`，还实现了 `/v1/responses`（Codex 用）、`/v1/messages`（Anthropic 协议，Claude Code 用）、`/v1/embeddings`、`/v1/audio/*`、`/v1/videos`。一条 `rapid-mlx launch claude-code` 就能自动改写本地配置，把 Claude Code 的请求路由到本机模型。LangChain、PydanticAI、smolagents 三个 Python 框架也做了在线验证。

### 5. 不止文本：视觉、音频、视频、嵌入全模态

基础安装仅 460MB（纯文本），按需扩展：`rapid-mlx[vision]` 支持 Qwen-VL 等多模态模型；音频 STT/TTS 内置 26 个模型别名；甚至能跑 LTX-2.3 文生视频（需 24GB+ 内存）。模型目录覆盖 **165+ 文本别名、30+ 模型家族**，DeepSeek V4 Flash 这样的新模型做到 Day-0 支持——158B-A13B MoE 在 128GB Mac Studio Ultra 上以 2bit 量化跑出 56 tok/s，支持 1M 上下文。

### 6. `rapid-mlx share`：一条命令把本地模型分享到公网

内置 HTTPS 隧道，`rapid-mlx share qwen3.6-27b-8bit` 即可把 Mac Studio 上的模型安全暴露给远程设备或编辑器——家里的 Mac 变成团队的私有推理服务器。

## 技术亮点

### 1. 自动配置引擎：零配置的背后是"模型指纹识别"

DeepWiki 架构解析显示，`detect_model_config` 工具会检查模型元数据，**自动选择正确的 tool_call_parser 和 reasoning_parser**，自动应用提示缓存和 KV 量化策略。用户只需要 `rapid-mlx serve qwen3.5-9b`，不需要知道 Qwen 的工具调用格式和 Hermes 有什么区别——复杂度被引擎吃掉了，这是它比裸用 mlx-lm 体验好一个量级的原因。

### 2. 流式推理分离：`<think>` 标签实时路由

针对 DeepSeek-R1、Qwen3 等推理模型，`StreamingPostProcessor` 和 `StreamingThinkRouter` 在流式生成过程中实时剥离特殊 token，把思维链内容路由到 API 的 reasoning 字段、正文路由到 content 字段——客户端拿到的是结构化的"思考/回答"分离输出，而不是混在一起的原始文本。

### 3. DFlash 投机解码：按模型家族逐一验证，拒绝"静默出错"

块扩散投机解码在 Qwen3.5/3.6 27B 上实测带来 1.31-1.49 倍吞吐增益。值得称道的是工程态度：**opt-in 且按模型家族逐个验证**，而不是全局开启——因为错误应用投机解码会产生"没有报错的错误输出"，这种克制在追求跑分的推理引擎里很稀缺。

## 快速上手

```bash
# 方式一：一键安装（自动检测内存并推荐模型）
curl -fsSL https://rapidmlx.com/install.sh | bash

# 方式二：Homebrew
brew install rapid-mlx

# 启动服务（16GB Mac 推荐）
rapid-mlx serve qwen3.5-4b-4bit

# 任何 OpenAI 客户端直接调用
curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "qwen3.5-4b", "messages": [{"role": "user", "content": "你好"}]}'

# 一键接入 Claude Code
rapid-mlx launch claude-code
```

内存选型参考：8-23GB 跑 4B 级、24-47GB 跑 20B 级、48-95GB 跑 35B 级、96GB+ 可上 120B 级。

## 对比分析

| 维度 | Rapid-MLX | Ollama | LM Studio | mlx-lm（上游） |
|------|-----------|--------|-----------|---------------|
| **底层引擎** | 纯 MLX（UMA 原生） | llama.cpp | llama.cpp/MLX 混合 | MLX |
| **Qwen3.5-9B 速度** | 108 tok/s | 46 tok/s | — | 62 tok/s |
| **缓存 TTFT** | 0.08-0.16s | 无提示缓存（~0.5s） | 无 | 无 |
| **工具调用** | 17 种解析器，自动恢复 | 基础支持 | 基础支持 | 需自行处理 |
| **推理分离** | 流式 think/content 路由 | 无 | 部分 | 无 |
| **连续批处理** | ✅ | ❌ | ❌ | ❌ |
| **API 协议** | OpenAI + Anthropic 双协议 | OpenAI 子集 | OpenAI 子集 | 无服务端 |
| **平台** | 仅 Apple Silicon | Mac/Linux/Win | Mac/Win | 仅 Apple Silicon |
| **模型库** | 165+ 别名/30+ 家族 | 最全 | GGUF 生态 | HF 全量 |
| **开源协议** | Apache-2.0 | MIT | 闭源客户端 | MIT |

一句话总结：**Ollama 赢在生态和跨平台，Rapid-MLX 赢在 Apple Silicon 上的绝对性能和 Agent 工程化**。如果你的设备是 M 系 Mac、主力场景是编码助手和本地 Agent，Rapid-MLX 几乎是无脑升级；如果团队里有 Windows/Linux，或依赖长尾模型，Ollama 仍是更稳的选择。两者并不互斥——不少开发者用 Rapid-MLX 跑主力模型、留 Ollama 做兼容性测试。

也要说清楚局限：仅支持 Apple Silicon（无 Intel/Windows/Linux）；模型库长尾覆盖不如 Ollama；项目仅 5 个月、迭代极快（467+ commits），API 和行为可能变动；官方基准均为自测数据，独立第三方评测还不多。

## 写在最后

这个项目最有启发的地方有两点。

第一，**"平台专用"是性能的杠杆，不是包袱**。Ollama 用一套 llama.cpp 通吃三平台，代价是任何平台都拿不到极致性能；Rapid-MLX 反其道而行，赌注全押 Apple Silicon 的统一内存架构，换来 2-4 倍的性能差距。在"通用性"被过度崇拜的时代，敢于收窄目标平台反而打开了优化空间——这个思路对做端侧 AI 的团队很有参考价值。

第二，**本地推理的竞争焦点正在从"能跑"转向"好用"**。170 tok/s 的裸速度只是入场券，Rapid-MLX 真正的护城河是那些"脏活"：17 种工具调用格式的逐一适配、11 个 Agent CLI 的端到端回归测试、投机解码的按家族验证。当本地模型的能力逼近云端，决定胜负的就是这些工程细节——谁能让 Claude Code 无感切换到本地模型，谁就抓住了下一波端侧 AI 的入口。

如果你手上有一台 M 系 Mac，花 5 分钟装一个试试——`brew install rapid-mlx`，你可能会重新认识自己这台机器的算力。
