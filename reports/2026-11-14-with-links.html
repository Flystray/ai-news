iPhone 是公认最难被自动化主流的手机：没有 ADB，不许可靠的侧载调试通道，苹果连自家的 Siri 都只开放给主动接入的开发者。一个叫 Henry Yuan 的开发者给出的解法出乎意料——不碰系统、不越狱、运行时甚至不需要电脑，只花约 7 美元（淘宝 40–50 元，据什么值得买社区实测）买一块 ESP32-S3 开发板插在手机上，让 AI 像人一样"看着屏幕、动手去点"。项目 10 月 11 日建仓，一个月零三天攒下近 5,000 star，被 Hackaday、阮一峰《科技爱好者周刊》第 415 期、Hackster.io 先后报道，HN 上也有独立讨论。最有意思的一点是：整个方案没有用任何苹果的私有接口，"眼睛"是标准 AirPlay，"手"是标准 USB 鼠标键盘协议——苹果没留门，它贴着三扇正门各开了一条缝。

项目背景：开发者能忍，普通人过不去的 Xcode 那一关

市面上 iPhone 自动化方案几乎都走同一条路：电脑 + 调试通道。WebDriverAgent、mobile-mcp、Midscene 这类工具，第一次上手要装完整 Xcode、打开开发者模式、USB 配对信任，然后在终端里敲命令；之后每次运行，电脑都得开着、连着线或连着网。README 里有一句很直白的判断：开发者能忍，普通人基本卡在第一步。

这不只是体验问题。2026 年了，AI agent 已经能替人写代码、订机票，但让它帮你 iPhone 上的记账 App 记一笔、把网课听一遍，门槛反而比十年前的安卓脚本还高。安卓侧有 ADB，一套 open-adb 方案加 Droidline 这类手机端配合的 App 就能跑起来；iOS 侧的封闭让"AI 用手机"这件事在最大的封闭生态里长期缺位。

esp32-iphone-agent 的作者把问题拆成了三件硬件本事：看（眼睛）、动（手）、想（大脑）。前两件交给一块 40 元的 MCU，第三件交给任意 OpenAI 兼容的视觉模型。整条链路不越狱、不要开发者账号、不用 Mac 常驻，也不修改 iOS 的任何字节——它能跑，靠的是苹果官方就开放的三个能力：屏幕镜像（AirPlay）、辅助触控（AssistiveTouch）、USB HID 外设。

核心功能

1. AirPlay 眼睛：开发板伪装成一台屏幕镜像接收器

ESP32-S3 开机后自建 Wi-Fi 热点，在 iPhone 的"屏幕镜像"列表里以 ESP32 Agent 的身份出现。手机推流过来后，板子不做任何解码，把 H.264 码流原样经 Wi-Fi（TCP 7201 端口）转回手机上同装的 ESP32 Agent App。画面规格是 480×1040、最高 5 fps（README 自述），对人看是缩水了，对视觉模型判断界面元素刚好够用。

2. USB HID 手：一块标准鼠标键盘 + 辅助触控

开发板经 TinyUSB 枚举成标准 USB 鼠标和键盘，插在手机上、由手机供电。开启 iOS 的辅助触控后，屏幕出现一个虚拟指针：鼠标点一下等于手指轻点，按住拖动等于滑动，键盘则负责打字。这是整套方案里最"投机取巧"也最稳的一环——iOS 对外接鼠标键盘的支持是官方功能，谁也封不掉。

3. App 大脑：planner + actor 双模型循环

手机上的 SwiftUI App 解码画面、截图发给任意 OpenAI 兼容视觉端点（云 API、vLLM、Ollama 都行），跑 planner（规划）+ actor（执行）两级循环，动作集包括 tap、swipe、draw、type、按键、回主屏、结束。planner 和 actor 可以分别指定模型——README 明确说"图像 token 主导成本"，给 planner 配便宜模型、actor 保留强模型是官方推荐的成本权衡。

4. 闭环控制：晃一下指针再落点

HID 指针是相对坐标，App 会在精确点击前先"晃动"指针、从镜像画面里找到它、校正偏差后再落点；每次动作后等待屏幕稳定并回报"画面有没有变化"，失败会重新规划。链路断掉（板子掉线、热点丢失）会暂停任务，恢复后从同一步继续。这套纠错逻辑是它比早期同类方案（每指令一次点击、无校验）更可靠的关键。

5. 能听、能回放、能被别的 agent 调

App 1.0.2 起支持转发 AirPlay 音频、由手机本机转成文字，听力题和语音提示能处理；每次运行在手机上留有逐步回放，可导出截图与动作轨迹给另一个 agent 做复盘。仓库同时是一个 MCP server（npx -y esp32agent mcp），Claude Code、Cursor 等 coding agent 可以直接把这块板子当成"iPhone 工具"用，也有 DeepSeek Harness 插件版。

6. 任务固化到 Siri 和快捷指令

常用任务可保存，从 Siri、快捷指令、小组件、控制中心一键触发。作者放出的演示是一台真 iPhone 自己上完一节多邻国课程，8 倍速，全程无人碰屏幕。

技术亮点

1. 把"电脑的活"塞进一块 7 美元 MCU，代价是明确取舍

最早版本（tag v0.1.0）跑在电脑上：Mac/Linux 起 UxPlay + Python server。现在的架构把镜像接收、指令执行全部下放到板子，App 装在手机上，运行时彻底去电脑化。代价写得清楚：板子不解码 H.264（省算力），所以画面只能 passthrough 回手机；Wi-Fi 被热点占用，模型流量只能走蜂窝；每步耗时数秒，主要花在模型上。Hackaday 在 2026-10-14 的报道里评价这种做法"听起来绕，但免掉了开发者账号、Xcode 和 Mac 这套包袱"——那篇报道描述的还是早期电脑版，现架构是其后重构的，读旧报道时注意时间差。

2. 全程贴着官方接口走，不与苹果对抗

方案没有一行代码碰私有 API：AirPlay 接收器移植自开源项目 UxPlay（GPL-3.0），输入走标准 USB HID，点击靠辅助触控。这意味着系统更新不容易把它打死——苹果若改动，也只会沿公开协议的路径改。这是它与越狱类方案最本质的区别，也是它三个月内没被苹果"封杀"的现实原因。当然，这层依赖是双刃剑：苹果在系统层面收紧镜像或外设策略时，项目没有对抗手段，这一点 README 未做承诺。

3. 自带复盘数据管线

每次运行记录 planner/actor 调用次数、带截图的请求数、endpoint 报告的 token 用量（缺失标 partial，不强制补 0），支持批量导出 trace 供另一个 agent 分析。对做 agent 研究的人，这比"能用"更有价值：失败步骤在哪一步、图像 token 花了多少，都有原始数据。

适用人群

  • iOS 自动化受困者：受够了"装 Xcode→开发者模式→配对"三件套，想给家里老人手机做自动签到、自动打卡，一块板子加 TestFlight 就能跑，省掉整套电脑环境。
  • 视觉 agent 研究者：想要一个真实手机 GUI 环境 + 完整 trace 导出的实验台，省掉自建采集链路；本地模型（Ollama/vLLM）可直接接。
  • 无障碍探索者：辅助触控 + 物理指针的路径天然对运动障碍用户友好，README 也把无障碍列为适用场景之一。
  • 硬件玩家：固件（Arduino 框架、NimBLE、TinyUSB）、BLE 协议文档（docs/ble-protocol.md）、免线开发 harness 都是现成教材。
  • coding agent 用户：让 Claude Code 通过 MCP 直接"看见并操作"你的 iPhone，做端到端 App 测试。

快速上手

前置：一台 iOS 18+ 的 iPhone（XS 及以上，USB-C 机型直插，Lightning 机型需相机转接器）、一块 Seeed Studio XIAO ESP32S3 标准版（8MB PSRAM，不是 Sense 也不是 Plus）、一台装了 Chrome/Edge 的电脑（仅烧录用一次）。

  1. 买板子。注意淘宝买回来先装上天线，什么值得买社区的实测特别提醒：不装天线蓝牙会连不上或只能贴着手机用。
  2. 浏览器烧录：打开 handsy.tech/install，点 Connect board，约 30 秒，无需 IDE 和驱动。连不上就按住 BOOT 键再插。
  3. 装 App：加入 TestFlight 公测（App Store 正式版在审核中），按 App 内四步引导走：蓝牙配对 → 加热点开屏幕镜像 → 开辅助触控校准 → 填模型 endpoint 和 key（存 Keychain）。
  4. 输入任务按 Start。想接进 coding agent 就加 MCP：claude mcp add esp32agent -- npx -y esp32agent mcp。

常见坑：免费共享模型线路繁忙时会 503，任务卡住或每步失败，换自己的 API key 即可（Settings › Model）；免费 Apple ID 签名版每 7 天要重签；热点下无互联网是设计如此，模型流量走蜂窝。

表格之后说句实话：如果你的目标设备是安卓，这个项目对你是"参考架构"而非工具——它解决的是 iOS 这个空白生态的准入问题。如果你的 iPhone 任务大多是输入长文本、横屏应用或支付场景，它目前的形态接不住（原因见下）。它真正的甜点区是：重复、竖屏、无需精细输入的日常操作。

局限

把丑话说在前面，以下均有出处。

  • 画面规格低：480×1040、最高 5 fps，每步耗时数秒，主要花在模型推理（README 自述）。
  • 系统界面不可见：密码输入、Apple Pay、DRM 视频、锁屏状态都不镜像，agent 看不到（README 自述）——支付类自动化天然出局。
  • 不支持横屏应用：坐标与校准假定竖屏（README Roadmap 未完成项）。
  • 中文输入是拼音：经开发板键盘以拼音输入，ctrl+space 切中英，不用剪贴板，emoji 直接丢弃（README 自述；什么值得买社区把这点写进了标题）。
  • Wi-Fi 被占用：运行时手机只能走蜂窝数据访问模型，流量与信号都是隐性成本。
  • 免费线路不稳：共享线路高峰期 503，任务可能整轮失败（README 自述）。
  • 实测反馈的硬件细节问题：open issue 里已有指针灵敏度校准不准（#115）、点击前落点校验需加强（#104）、Windows CLI 蓝牙扫描返回空列表（#114）等真实抱怨，截至 2026-11-14 该仓库 open issue 共 15 个，多数还挂着未合。
  • 媒体信息滞后：Hackaday 报道描述的是 10 月 14 日的电脑版架构，与当前代码差异较大，引用时需核对版本。
  • 合规边界：README 要求只自动化自己拥有或被授权的设备与账号；用模拟输入绕过 App 的使用条款属于灰色地带，商业使用前自行评估。另外作者自述项目开发用的是两台 DGX Sparks 上服务的 nvidia/Qwen3.8-Flash-Next-NVFP4（README 自述），个人用户复现成本不低，但不影响用云端模型。

写在最后

两点判断。其一，这个项目证明了一件事：在平台不开放的时代，"物理外设"仍是 agent 落地最硬的桥——不碰系统、不逆协议，一块 40 元的 MCU 就能把封闭生态里最难的"准入"问题变成本来的样子：一个外设问题。它没解决 iOS 自动化的全部问题，但把"普通人能不能让 AI 用手机"从否命题改成了开放命题。其二，planner/actor + 截图反馈 + trace 导出这套手机 GUI agent 的工程范式，比板子本身更值得搬走，安卓侧和桌面侧都能复用。

具体建议：动手派买板子走 TestFlight 三步流，一小时内能看到 AI 替你点屏幕；做研究的直接看 docs/ble-protocol.md 和 trace 导出格式；只想围观实践的，先读 issue 区——那里是目前最诚实的"第二份文档"。
