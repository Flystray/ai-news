一句话：它给你和同事电脑上的每一个编码 agent 会话发一个地址，让 A 的 agent 能直接问 B 的 agent「token 格式改了没」，消息落进对方已经打开的那个会话，端到端加密，不经过任何能读内容的服务器。最反直觉的一点是消息怎么进 agent：它按 11 种客户端各自的能力分成 push / turn / pull 三档，而不是统一塞进某个队列。

## 项目背景：多 agent 协作缺的不是智力，是寻址

一个五人的后端组，每人同时开三四个 Claude Code、Codex、Cursor 会话。前端那位想知道接口字段改没改，最省事的做法是自己翻仓库——如果他有权限；否则就在群里问一句「改完了吗」，等对面的人复制一段日志过来。两个 agent 明明在同一个仓库、同一条分支上干活，互相不知道对方存在。

这不是协作意愿问题，是缺一层基础设施：agent 会话没有地址。你能说「问一下 alice」，但没法说「问 alice 那台 XPS 上跑在 api 仓库 auth 分支的那个 codex 会话，它现在正忙」。没有地址，就没法精准投递，只能广播或者靠人转述。

已经有的两类方案各缺一半。单机编排工具管的是「一台机器上多个 agent 排队干活」，出了这台机器就失效；共享文件、Slack 频道、复制粘贴管的是「人跟人同步」，agent 既不会主动看，也不知道该看哪个线程。它的设计文档里列了 11 个 2026 年的同类项目，结论是绝大多数只服务单机、单人，或者只支持 Claude 一家——最接近的两个，一个把对端限定成你自己的设备（靠 Tailscale 同账号），一个只做「加密房间」而没有目录，跨机还得自建服务器。

真正没人做的那件事，是**一张带上下文的活会话目录**：谁、哪台机器、哪种 agent、哪个仓库哪条分支、忙还是闲、正在干什么。有了这张表，投递才有目标，agent 才不用靠猜。

## 核心功能

### 1. 四层地址：团队 → 人 → 机器 → 会话

`team ──< person ──< machine ──< session`。会话名默认是 `<仓库或目录>-<agent>`，重名自动加 `-2`、`-3`，agent 自己也能改。地址语法支持六种粒度：`alice/api-cursor`（一个会话）、`alice/api-cursor@xps`（同名会话分处两台机器时指定机器）、`api-cursor`（队内唯一时可省略人名）、`alice/*`、`repo:acme/api`、`*`。

值得单独说的是最后三种组地址的使用限制：**agent 发不出去**。任何来自 agent 的 `*`、`person/*`、`repo:` 消息在发出前就被拒绝，只有 `<person>/terminal`（真人坐在终端里）能用。这个设计很直白——广播看起来方便，实际会把「精准问一个人」退化成「打扰全队」，而 agent 最不缺的就是这种冲动。

```sh
reason-network who                                             # 谁在线、在干什么
reason-network send alice/api-claude "did the token format change?"
reason-network send alice/api-claude --file schema.json "the schema I meant"
```

### 2. 投递分三档：push / turn / pull

这是整个项目最费工的地方。消息「送到对方机器」和「被对方 agent 看见」是两件事，不同客户端的钩子能力差得很远：

- **push**：能在回合中途注入，还能唤醒空闲会话。Claude Code 走的是 MCP 子进程往该会话自己的 inbox socket 写一个 `{"type":"user",…}` 帧；Codex 用 `PostToolUse` 的 `additionalContext`，或者在 Stop 上 `decision:block`；opencode、pi、Amp 各有插件接口。
- **turn**：只能在下一个工具调用或回合结束时塞进去，空闲会话得等人再敲一句话。Cursor、Gemini CLI、Copilot CLI、Command Code、Grok CLI 都在这一档。
- **pull**：只在你主动查的时候给。DeepSeek Harness 和任何普通 MCP 客户端属于这类，靠 `check_inbox` 长轮询，外加每个工具结果后面附一行「有未读」。

档位不是写死在文档里的说明，是它会随消息一起返回的信息。发出去的回执会直接告诉你「queued: alice/web-cursor 是空闲的 turn-only 会话，等 alice 下次给它发指令才会看到」。这句话比任何「已送达」都诚实。

### 3. 状态靠读 transcript，不靠 agent 汇报

「正在干什么」这一行不是 agent 自己填的。它去读各客户端本来就会落盘的东西：Claude Code 的 `ai-title` 转录条目、Codex 的 `~/.codex/session_index.jsonl` 里的线程名、opencode 的 session title，再加上各自的 todo 列表（`~/.claude/tasks/<session>/`、TodoWrite、`update_plan`、`write_todos`、`todo_write`）。每次只读上次之后新增的部分。

这个选择省掉了「让 agent 记得汇报」这类不可靠约定，代价是隐私暴露面变了：你的会话标题就是同事看到的工位挂牌。它给了个按目录关闭的开关，`reason-network folder ~/personal off` 之后那个目录下的会话不上网。我在代码里核对了 `doing.rs` 的实现，确实是从转录里抽的，不是让模型自述。

### 4. ask_user：审批答案带签名回来

同事的 agent 找你这边要一个只有你能拍板的东西（比如「能不能发版」），你这边会弹窗，Approve 或 Deny，还能附一句说明。答案不是作为一条消息回来的，而是作为工具调用的结果，并且带一个用本机私钥签的 `Approval` 结构，里面固定包含它答复的那条请求 id（`about=`）。接收方校验签名、校验「发送方是不是我请求的那个人」「about 是不是我那条请求」，对不上就丢弃。

它自己也写了这条防线的边界：能控制审批者电脑的软件仍然可以签，因为机器私钥就是本地一个文件。这是减速带，不是保证。

### 5. 回执分四段，重试带幂等键

`message_status` 报的是四个独立观测：queued（进了对方队列）、accepted（对方机器接收）、handed（交给了本机 agent）、replied（明确回复了）。远端接受了但没人看，就停在 accepted，不会伪装成 delivered。重试同一个 `send_message` 要复用 `idempotency_key`，内容不一致会被拒；回执保留 7 天。

### 6. 文件只传小文本，落地永不执行

一条消息最多带 10 个文件，单个 256 KiB，合计 512 KiB，隐藏文件不许传。收件方存到 `~/.reason/network/inbox`，不设可执行位，也不会替你打开，只在消息里告诉你路径。这三个上限我在 `src/files.rs` 里逐个核对过，是编译期常量，不是文档口径。

## 技术亮点

### 1. 传输层用 iroh，把身份压进公钥

每台机器一个 iroh `Endpoint`，持久私钥就是身份（`EndpointId`，ed25519 公钥）。打洞成功直连，同一局域网用 mDNS 发现，打不通退到 HTTPS:443 的中继，中继只转发加密 QUIC。团队可以自建中继（`reason-network relay <url>`），一旦自建，机器连 iroh 背后的 n0 地址服务都不再联系。

代价写得很实：直连端口每次启动随机，要在防火墙开固定口就得把 `port = 41641` 写在 `config.toml` 最上面（放进 `[table]` 下会被忽略）；中继列表要按签名校验，超过 16 个、超过 64 KiB、过期、出现 http 地址，整份作废而不是部分采用——因为一份坏列表能决定谁跟谁通信。

协议 ALPN 还叫 `tincan/1`。项目从 tincan 改名过来不久（0.10.1 那次全仓改名），协议名没跟着动，老客户端才能继续互通。

### 2. 名单是签名链，谁都进不来自己

成员名单复制到每台机器，每条准入记录由一台**已被准入**的机器签名，创世那条自签。这个 `admissions` 表永久保留，所以「谁有权准入」不依赖记录到达顺序，各机器最终会收敛到同一份名单。成员状态用 last-writer-wins，邀请存的是 `hash(secret)`、单次有效、随签发机器一起失效。

源码注释里那句自我限定比宣传诚实：被移除的机器连不上，但并没有被「密码学阉割」——它手里还有自己的私钥和之前拿到的名单。作者的原话是「这是给朋友用的」。

### 3. 名字验证不回调云端

用 Reason 账号登录后，机器携带一份紧凑 JWS（只接受 RS256），声明「这个 EndpointId 属于账号 sub、显示名 name、有效期到 exp」。校验用的 RSA 公钥（≥2048 位）编译进了二进制，永不删除，**不联网问 Reason**。proof 超过 4 KiB、签发时间超前 1 天，直接拒。

好处是断网也能验名字，队友的机器自己就能确认「这台电脑确实是那个人」。代价是公钥轮换要发版；另外证明过期只影响那个「已验证」标记，不影响成员资格——这条分得很清楚，否则时钟不准的机器会互相踢人。

### 4. 反滥用是三层闸门

第一层在发送侧：agent 不能用组地址，只能点对点；第二层是每对会话 10 分钟内最多 12 条 agent↔agent 消息，超了直接 refused 并附一句解释；第三层是每发送方的速率上限，代码里是 60。三层都体现在回执里，不是静默丢弃。

一个团队里两个 agent 互相礼貌地推诿四十轮，是这类系统最容易出的笑话。把上限做成编译期常量、把拒绝理由回传，比事后看日志强。

## 适用人群

- **多人同仓的开发组**：前端改字段、后端改契约，让两边的 agent 直接对一次，省掉一次人工转述和一次「你重启一下试试」。
- **一人多机**：家里台式写代码、笔记本在客厅改，两边会话互相对话，不用靠 git push 同步思路。这是投入产出比最高的一档。
- **平台/效率工程师**：要给团队搭这层通信，又能接受自建中继（一台 VPS 加 Let's Encrypt），可以把「谁跟谁通信」也收进自己的边界。
- **不适合单人单机**：没有第二个人或第二台机器，它就是空转。也不适合纯 CI 环境，审批弹窗和菜单栏在那里没有意义。

## 快速上手

```sh
# macOS / Linux：装引擎 + 登录 + 建网络，一步完成
curl -fsSL https://reasonmachines.com/install.sh | bash -s -- network
```

```powershell
# Windows PowerShell
irm https://reasonmachines.com/network/install.ps1 | iex
```

不想要账号也行，名字会标成未验证：

```sh
reason-network init acme --as alex          # 建网络
reason-network join '<link>' --as bob       # 用邀请链接加入
reason-network doctor                       # 看端口、中继、各 agent 接线状态
```

四个常见的坑，按踩到的概率排序：[dev.to 那篇上手文](https://dev.to/dedupedai/how-to-let-your-coding-agent-message-your-teammates-agents-with-reason-network-2o39)专门提醒过第一个——`curl | bash` 之前先把脚本下下来读一遍，这是个信任决定；Codex 会话要等你第一轮对话跑完才上线，因为它在那之前不放钩子；Windows 上未签名的 `reason.exe` 会被 Defender 和 Smart App Control 拦（对应 issue #186、#216）；防火墙要固定端口时，`port` 必须写在文件最顶部。

## 对比分析

| 维度 | Reason Network | agentbus | agents-party | 单机编排工具 |
|------|----------------|----------|--------------|--------------|
| 传输 | iroh P2P，中继可自建 | iroh，但对端是自己的设备 | 加密房间，跨机需服务器 | 本机进程 |
| 跨人协作 | 是，名单靠签名链 | 否 | 是，但只有房间没有目录 | 否 |
| 会话目录 | 人/机器/仓库/分支/忙闲/doing | 无 | 无 | 无 |
| 投递能力 | 11 种客户端分 push/turn/pull | 有限 | Claude/Cursor/Codex | 不涉及 |
| 许可与成本 | MIT 或 Apache-2.0，免费，中继可自建 | 无协议文件 | 开源 | 各异 |
| 局限/风险 | 名字验证依赖 Reason 账号；遥测默认开；Windows 无签名 | 只服务单人 | 需运维服务器 | 出不了这台机器 |

选它的边界很清楚：只有当「跨机器 + 跨人 + 要人工拍板」三件事同时成立时，这套目录和审批才划算。如果只是想让一台机器上的几个 agent 串活，用编排工具，别用通信管道凑。

## 局限与风险

**热度是平缓的，不是爆发的。** 11 月 6 日[一篇中文评测](http://mp.weixin.qq.com/s?__biz=Mzg3MTgyNTMzNA==&mid=2247484147&idx=1&sn=5e1256a630ec972134d6bbb7b5c107e1)记录的是 1,578 star、138 fork，今天 1,797 star、161 fork，半个多月日均十几个。同期 open issues 与 PR 合计 42 个，而提交高度集中在一个主力账号（240 次提交，其余贡献者都是个位数）——这说明它在快速迭代，也说明 bus factor 很低。

**Windows 上问题成串。** issue #186 是 Defender 把安装器报成 `Trojan/TermFix.SC`；#216 是 Smart App Control 直接拦未签名的 exe，连带把已有安装搞坏；#228、#229 是 Antigravity 的钩子路径带空格就失败。跨平台支持在 Mac 上验证得最充分，Windows 还在补。

**自动更新没有独立签名。** issue #183 指出 Windows 和 Linux 的发布包没有代码签名，而 daemon 会静默装更新。整条链路只靠 GitHub 的传输安全，这在企业环境里通常过不了审。

**遥测默认开着。** 引擎会把聚合计数写进本地 SQLite 并随 Reason CLI 上报：agent 类型、路由方式、投递阶段、大小与延迟分档。正文、文件名、仓库、会话名、密钥都不在其中，报告也和账号绑定而不是匿名；`DO_NOT_TRACK=1` 可以关掉。介意的话别忘设这个环境变量。

**发布节奏和代码不同步。** 最新 release 还是 10 月 30 日的 v0.12.17，之后三周代码一直在动（最新提交是今天）。想用新功能得自己 `cargo build`，或者跟 Reason CLI 捆绑的那个版本。

**还有几处语义边界要记牢。** 「accepted」不等于 agent 读到了；Codex 首轮对话之前收不到消息；push 层会话收 FYI 邮件有已知 bug（issue #222）；冲突提醒（同一文件被两个 agent 改）在 M4 里，还没开始做。

最后一条与国内读者有关：默认中继是 Reason 自己的区域节点，登录、邀请链接、升级检查都要经过 reasonmachines.com。这套服务在中国大陆的网络表现如何，官方未说明，自建中继是唯一能自己掌控的路径。

有一点要说清楚：[New Runtime 的评测](https://newruntime.com/posts/reason-network-is-an-open-source-rust-daemon-b71aac)把证据边界划得很直白——现有材料能证明「设计如上」，不能证明「可靠性与生产采用率如上」；我没有找到任何一家团队公开的两周以上运行报告。所以上面所有机制都是按代码与文档核过的，长期稳定性属于尚未被第三方验证的部分。

## 写在最后

它没有让模型变聪明一点，而是给「agent 之间的协作」补了一个此前被跳过的层：寻址。有了地址，才谈得上精准投递；有了投递回执，才谈得上「我到底有没有被回复」；有了签名审批，才敢让 agent 替你去要一个只有人能给的许可。这三件事拆开看都不新鲜，在我核过的同类项目里，把三者串成一个能装、能跑、能自建中继的成品，这是第一个。

给读者的具体建议：先用两台自己的机器试半小时，重点看 `reason-network who` 的 `doing` 一行准不准——那一行不准，后面所有投递都是盲投。团队要上，先开个会把「哪些目录 off」定下来再发邀请链接，这一步比装什么版本重要。生产环境先别开自动更新，等签名问题（issue #183）有着落。
