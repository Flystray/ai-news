1000 万条 1536 维的文档向量，以标准 float32 存储，需要 31 GB 内存。turbovec 把它压到 4 GB——压缩 8 倍，搜索速度还比 FAISS 快 12-20%。这不是营销话术，是 README 里可复现的基准测试数据。

这个数字之所以刺眼，是因为每一个搭过 RAG 系统的人都知道：LLM 推理本身已经不是瓶颈了，**向量存储才是**。你的 MacBook 能跑 7B 模型，但塞不下一千万条 embedding。turbovec 要解决的就是这个问题——而且它用的方法不需要训练、不需要码本、不需要重建索引。

---

## 项目背景：向量索引的"训练税"

几乎所有生产级向量量化器——包括 FAISS 的乘积量化（PQ）——都依赖一个痛苦的前提：**先训练码本，再编码数据**。你需要从语料中采样、跑 k-means 聚类、生成码本、编码全量向量。如果语料增长了？分布漂移了？对不起，重新训练、重建整个索引。

这不是小问题。在实际生产环境中，文档是持续流入的——今天加 5 万条产品描述，明天加 10 万条客服记录。每次都要停下来训练码本，意味着系统有一个"不可用窗口"。更尴尬的是，如果训练样本不能代表最终数据分布（几乎总是如此），召回率就会打折。

turbovec 的底牌是 Google Research 2025 年 4 月发表的 **TurboQuant** 算法（ICLR 2026 录用）。这是一个"数据无感知"（data-oblivious）量化器——它的量化方案完全来自数学推导，不依赖任何输入数据。这意味着：**没有训练步骤，没有码本，没有重建**。向量来了直接 add()，立即可搜。

## 核心功能

### 1. 零训练在线索引

调用 `index.add(vectors)`，向量立即被量化并进入索引。没有 `train()` 步骤，没有参数调优，没有"先喂 10 万条样本校准"的前置条件。TurboQuant 的量化桶边界是从数学公式预计算的，不随数据变化。这对流式写入场景（日志、实时文档管道）是决定性优势。

### 2. 2-4 bit 极致压缩

支持 2-bit 和 4-bit 两种量化宽度。1536 维 float32 向量从 6,144 字节压缩到 384 字节（2-bit）或 768 字节（4-bit），分别实现 16 倍和 8 倍压缩。1000 万条 1536 维向量：FP32 需 31 GB，4-bit 需约 4 GB，2-bit 需约 2 GB。

### 3. 手写 SIMD 内核

不是调库，是手写的汇编级内核。ARM 平台用 NEON 指令，x86 平台用 AVX-512BW 和 AVX2 指令。在 Apple M3 Max 上，turbovec 的 NEON 内核比 FAISS IndexPQFastScan 快 12-20%（单线程和多线程均胜）；在 Intel Sapphire Rapids 上，4-bit 配置下匹配或超过 FAISS。2-bit 配置在 x86 上略逊 FAISS 几个百分点。

### 4. 搜索时过滤

`search()` 接受 ID 白名单或 slot bitmask 参数。SIMD 内核在 32 向量块粒度上执行过滤——没有允许项的块直接短路跳过，不允许的向量在堆插入前丢弃。这意味着"先 SQL/BM25 筛选候选集，再用向量精排"的混合检索模式没有额外开销，不会过度取数，不会损失召回率。

### 5. IdMapIndex 稳定 ID

`TurboQuantIndex` 返回的是内部槽位 ID，`IdMapIndex` 在其上层提供稳定的 uint64 外部 ID。支持 `add_with_ids()` 和 `remove(id)`——删除操作 O(1) 完成，不需要重建索引。这对需要频繁更新（如文档删除/替换）的生产场景至关重要。

### 6. 持久化与双语言 API

`index.write("my_index.tv")` 和 `TurboQuantIndex.load("my_index.tv")` 提供简单的序列化。Python 端通过 PyO3 + maturin 构建 wheel，Rust 端直接 `cargo add turbovec`。两套 API 功能对等，版本独立演进（Python 0.8.0 / Rust crate 0.9.0）。

### 7. 纯本地隐私优先

没有托管服务，没有云端调用，数据不离开你的机器或 VPC。可以搭配任何开源 embedding 模型构建完全气隙的 RAG 栈——从 embedding 生成到向量存储到检索，全程不出内网。

## 技术亮点

### 1. TurboQuant 四步数学管道

这是整个项目最精妙的设计。TurboQuant 不适应数据——它用数学变换"抹平"数据差异：

1. **归一化**：剥离每个向量的范数，存为单个浮点数。向量变成高维超球面上的单位方向。
2. **随机旋转**：所有向量乘以同一个随机正交矩阵。旋转后，每个坐标独立遵循可预测的 Beta 分布（高维下收敛到高斯 N(0, 1/d)）——**无论输入数据是什么分布**。
3. **Lloyd-Max 标量量化**：因为旋转后的分布是解析已知的，最优量化桶边界可以纯数学预计算。2-bit = 4 个桶/坐标，4-bit = 16 个桶/坐标。不需要任何数据 pass。
4. **位打包**：量化后的坐标紧密打包成字节。

论文证明 TurboQuant 的失真率与香农下界极其接近，仅差一个微小常数因子。在 LongBench 上，3.5-bit 量化与 FP16 基线完全持平（50.06 vs 50.06 分）；在"大海捞针"测试中，4 倍压缩下检索准确率 0.997。

### 2. 跨架构 SIMD：一份代码两种指令集

turbovec 不是用 Rust 的 portable SIMD 抽象层偷懒——它为 ARM 和 x86 分别手写了内核。NEON 处理 128-bit 寄存器，AVX-512BW 处理 512-bit 寄存器，AVX2 作为 x86 基线回退。量化后的向量以 32 个为一组打包成块，SIMD 内核一次处理一个完整块，避免分支预测惩罚。过滤逻辑也嵌入内核：块级别短路 + 向量级别丢弃，在 SIMD 执行过程中完成。

### 3. 两阶段量化：MSE + QJL 残差校正

TurboQuant 论文的完整版本不只是纯标量量化。第一阶段用比目标位宽少 1 位的 MSE 量化器压缩；第二阶段对残差向量应用 1-bit 的 Johnson-Lindenstrauss 变换（QJL），提供无偏的内积估计。这个设计在极低比特（2-bit）下仍能保持高召回——d=3072 2-bit 召回率 0.912，超过 FAISS 的 0.903。

## 适用人群

- **RAG 系统开发者**：语料量超过百万级，float32 内存撑不住，又不想引入 Milvus/Qdrant 等重量级向量数据库

## 快速上手

**Python（最常用）**：

```bash
pip install turbovec
```

```python
from turbovec import TurboQuantIndex
import numpy as np

# 创建索引：1536 维，4-bit 量化
index = TurboQuantIndex(dim=1536, bit_width=4)

# 在线添加向量——无需训练，立即可搜
index.add(np.array(vectors, dtype=np.float32))
index.add(more_vectors)  # 随时追加

# 搜索
scores, indices = index.search(query, k=10)

# 带过滤的搜索（只搜允许的 ID 子集）
scores, indices = index.search(query, k=10, filter_ids=allowed_ids)

# 持久化
index.write("my_index.tv")
loaded = TurboQuantIndex.load("my_index.tv")
```

**需要稳定外部 ID 时**：

```python
from turbovec import IdMapIndex
import numpy as np

index = IdMapIndex(dim=1536, bit_width=4)
index.add_with_ids(vectors, np.array([1001, 1002, 1003], dtype=np.uint64))
scores, ids = index.search(query, k=10)
index.remove(1002)  # O(1) 删除
```

**Rust**：

```bash
cargo add turbovec
```

```rust
use turbovec::TurboQuantIndex;

let mut index = TurboQuantIndex::new(1536, 4);
index.add(&vectors);
let results = index.search(&queries, 10);
```

**前置要求**：Python ≥ 3.9，64 位平台，向量维度必须为 8 的正整数倍，x86 构建以 AVX2 为基线。

## 对比分析

| 维度 | turbovec | FAISS (IndexPQFastScan) | Milvus/Qdrant | float32 暴力搜索 |
|------|----------|------------------------|---------------|-----------------|
| **10M×1536d 内存** | 4 GB (4-bit) / 2 GB (2-bit) | ~6 GB (PQ 4-bit) | 8-12 GB（含索引开销） | 31 GB |
| **训练步骤** | 无，add() 即可搜 | 需 k-means 训练码本 | 需配置索引参数 | 无 |
| **新增向量** | 直接 add()，立即可搜 | 需重新训练或用 IVF 增量 | 支持但复杂 | 直接追加 |
| **分布漂移** | 无影响（数据无关） | 需重建索引 | 需重新配置 | 无影响 |
| **ARM 性能** | 比 FAISS 快 12-20% | 基准线 | 未优化 ARM | 慢（O(n) 扫描） |
| **x86 性能** | 4-bit 匹配/超过 FAISS | 基准线 | 依赖索引类型 | 慢 |
| **召回率 (d=3072, 2-bit)** | 0.912 | 0.903 | N/A（用 PQ/HNSW） | 1.0（精确） |
| **过滤搜索** | SIMD 内核内过滤，无额外开销 | 支持 but 有过度取数问题 | 支持 | 手动过滤 |
| **部署复杂度** | pip install，纯库 | 编译复杂，纯库 | 需独立服务进程 | 最简单 |
| **数据隐私** | 纯本地，气隙可用 | 纯本地 | 可自托管但需服务 | 纯本地 |
| **生态集成** | pg_turbovec, LangGraph 等 14+ 衍生 | 最成熟，各框架默认支持 | 原生集成各框架 | N/A |

turbovec 的定位非常清晰：它不是要替代 Milvus 或 Qdrant 这样的向量数据库——那些系统提供分布式、高可用、事务等企业级能力。turbovec 是一个**嵌入式向量索引库**，定位类似于 FAISS，但用"零训练 + 极致压缩"的差异化能力切入 RAG 基础设施层。如果你的场景是"单机跑千万级向量、内存有限、数据持续流入、隐私要求高"，turbovec 几乎是目前唯一的选择。

## 写在最后

turbovec 最值得关注的不是它的 Star 数（4 个月 14.4k 已经很快了），而是它代表的趋势：**学术论文到生产级工具的转化周期正在急剧缩短**。TurboQuant 论文 2025 年 4 月发布，2026 年 3 月被 ICLR 录用，turbovec 2026 年 3 月底就上线了可安装的 Python wheel 和 Rust crate——从论文到 `pip install` 只用了不到一年。

更重要的是，turbovec 证明了一件事：在 AI 基础设施领域，最锋利的武器未必是更大的芯片或更多的显存，也可以是**更聪明的数学**。一个随机正交旋转 + Lloyd-Max 标量量化的四步管道，就把 31 GB 的向量数据压到 4 GB，还跑得比训练了码本的 FAISS 更快。这不是工程堆砌的胜利，是数学直觉的胜利。

如果你正在搭 RAG 系统，或者只是对"数据无关量化"这个概念好奇，turbovec 值得花一个小时认真读读。那个 `pip install turbovec` 之后的世界，和之前不太一样。
