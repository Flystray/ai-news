### 📌 项目背景

AI 编程助手（Claude Code、Cursor、Copilot 等）在处理复杂项目时，有一个被长期忽视的致命问题：**工具输出正在悄悄填满你的上下文窗口**。

来看一组实测数据——

| 工具调用类型 | 原始数据量 | 相当于 Context 消耗 |
|---|---|---|
| 1 次 Playwright 快照 | 56 KB | 14K tokens |
| 20 条 GitHub Issues | 59 KB | 14.7K tokens |
| 单条访问日志 | 45 KB | 11K tokens |
| 81+ 次工具激活后 | 143 KB | 36K tokens（72%） |

工作 30 分钟后，**40% 的上下文已被工具输出污染**。当 Agent 不得不"压缩"对话来腾出空间时，它会遗忘：正在编辑哪个文件、任务进度到哪了、什么错误已经解决、用户最后要求了什么。状态丢失 = 重复劳动 = 效率归零。

Context Mode 的作者在 HN 上说："Cloudflare 用 Code Mode 证明了**输入侧**（工具定义）可以压缩 99.9%。我们想问：**输出侧**呢？"

这就是 Context Mode 诞生的起点——**一个专门解决工具输出侧上下文污染的 MCP Server**。项目在 2026 年 2 月上线，HN 拿到 570+ 分，获得 14.9k Stars，被 Microsoft、Google、Meta、Amazon、NVIDIA、ByteDance、Stripe 等头部公司开发者使用。

### 🚀 核心功能

**1. Context Saving（上下文节省）——98% 压缩率**

Context Mode 用**沙箱隔离**拦截原始数据，只将压缩后的摘要传入上下文窗口：

```
工具调用 → 隔离子进程执行 → 原始数据留在沙箱 → 仅 stdout 摘要入 context
```

单次操作压缩实测：
| 操作 | 原始大小 | 压缩后 | 节省率 |
|---|---|---|---|
| Playwright 快照 | 56 KB | 299 B | **99.5%** |
| GitHub Issues × 20 | 59 KB | 1.1 KB | **98.1%** |
| 访问日志 × 500 | 45 KB | 155 B | **99.7%** |
| CSV 分析 × 500行 | 85 KB | 222 B | **99.7%** |
| Git 日志 × 153次提交 | 11.6 KB | 107 B | **99.1%** |

全会话综合效果：**315 KB → 5.4 KB，节省 98.3%**；会话时长从 ~30 分钟延长至 **~3 小时**（6 倍提升）。

**2. Session Continuity（会话连续性）**

当 Agent 压缩对话时，所有工作状态都会**完整保留**：

- 所有文件编辑、Git 操作、任务状态、错误、用户决策 → 记录到 SQLite 数据库
- 压缩后重新连接时，通过 FTS5 搜索只取**相关事件片段**
- Agent 从中断处继续，无需重新开始

事件按 4 级优先级分配 2KB 预算：P1 关键（文件/任务/规则/用户指令，1KB）、P2 高（决策/Git/错误，700B）、P3 普通（MCP工具/子代理，200B）、P4 低（意图/角色，100B）。

**3. Think in Code（用代码思考）**

核心范式转变：**不要让 LLM 读取数据，让代码去处理数据**。

```js
// ❌ 传统：47 × Read() 调用 = 700 KB context 消耗
// ✅ Context Mode：1 × ctx_execute() = 3.6 KB
ctx_execute("javascript", `
  const files = fs.readdirSync('src').filter(f => f.endsWith('.ts'));
  files.forEach(f => console.log(f + ': ' +
    fs.readFileSync('src/'+f,'utf8').split('\n').length + ' lines'));
`);
```

从"读 50 个文件来数函数"变为"写一段脚本分析一切"——context 节省 100 倍。

**4. Output Compression（输出压缩）**

对 Agent 自身输出也进行压缩，去除填充词（just/really/basically）、客套话、犹豫表达，压缩率 **65-75%**。保留规则（安全警告、不可逆操作）自动展开，不影响关键信息传达。

**5. Knowledge Base（智能知识库）**

- `ctx_index`：将 markdown 内容按标题分块，存入 SQLite FTS5
- `ctx_search`：BM25 排序检索，8 级渐进回退（Porter AND → OR → Trigram → 模糊纠正）
- `ctx_fetch_and_index`：抓取 URL → HTML 转 markdown → 分块 → 索引，24h TTL 缓存

**6. 11 个 MCP 工具**

| 工具 | 功能 | 典型节省 |
|---|---|---|
| `ctx_execute` | 12种语言沙箱执行 | 56KB → 299B |
| `ctx_batch_execute` | 批量命令+搜索 | 986KB → 62KB |
| `ctx_execute_file` | 沙箱内处理文件 | 45KB → 155B |
| `ctx_index` | FTS5 内容索引 | 60KB → 40B |

### ⚙️ 技术亮点

**亮点一：三层过滤叠加架构**

Context Mode 的 98% 压缩率不是单一技术，而是三层过滤的叠加：

- **第一层：进程隔离**（~50% 节省）——代码在独立子进程中执行，stderr 完全隔离，仅 stdout 返回
- **第二层：智能截断**（~30% 额外节省）——`smartTruncate()` 对超阈值输出自动截断
- **第三层：意图驱动索引**（~18% 额外节省）——超过 5KB 的输出自动 FTS5 索引，仅返回 intent 匹配片段

三层叠加 = 98.3% 总节省。

**亮点二：FTS5 + BM25 搜索的 8 级回退策略**

知识库采用 SQLite FTS5 虚拟表 + BM25 概率排序算法，具体回退链路：

1. Porter 词干 AND（精确匹配）
2. Porter 词干 OR（扩大范围）
3. Trigram 子串 AND（容错拼写，如 "useEff" → "useEffect"）
4. Trigram 子串 OR（部分匹配）
5. Levenshtein 模糊纠正（自动修正拼写错误）
6. 用纠正后查询重试步骤 1-4

Smart Snippets：利用 FTS5 的 `highlight()` 函数，用 `\x02`/`\x03` 字节标记匹配位置，系统提取**围绕关键词的语义窗口**，而非天真地从开头截断。

**亮点三：15 个平台适配器 + Hook 生命周期拦截**

Context Mode 支持 15+ AI 编程平台，采用统一 Hook Adapter 接口：

| 平台 | Hook 覆盖 | 会话完整性 |
|---|---|---|
| **Claude Code** | 4/4（全） | Full |
| **Gemini CLI** | 4/4（全） | High |
| **VS Code Copilot** | 4/4（全） | High |
| **Cursor** | 2/4（缺 PreCompact/SessionStart） | Partial |
| **OpenCode** | 3/4 | Full |
| **Codex CLI** | 0/4（仅指令文件） | None |
| **Zed** | 0/4 | None |

每个平台通过 `routePreToolUse()` 拦截原生工具调用，自动重定向到沙箱工具——**非侵入式集成**，无需修改 AI 平台本身的代码。

### 🔍 对比分析

**vs Cloudflare Code Mode（输入侧压缩）**

Cloudflare 解决的是**工具定义**（输入侧）的压缩，Context Mode 解决的是**工具输出**（输出侧）的污染。两者互补，共同构成完整的上下文优化方案。

**vs 传统 RAG**

| 维度 | Context Mode | 传统 RAG |
|---|---|---|
| 触发时机 | 工具输出**即时拦截**，完全不进 context | 检索阶段才介入 |
| 数据结构 | SQLite 事件日志 + FTS5 BM25 | 向量数据库 + 相似度搜索 |
| 恢复方式 | BM25 精确检索相关事件 | 全量向量相似度 |
| 输出压缩 | ✅ 65-75% 模型输出压缩 | ❌ 无 |
| 适用场景 | 编程 Agent 上下文管理 | 文档问答、知识库检索 |

**vs 不使用任何优化**

| 指标 | 无优化 | Context Mode |
|---|---|---|
| 30 分钟后 Context 剩余 | **40%** 已被污染 | **99%** 清洁 |
| 会话持续时间 | ~30 分钟 | **~3 小时** |
| 典型会话总输出 | 315 KB | **5.4 KB** |
| 子代理调用（仓库研究） | 37 次 | **5 次** |

### 💡 行业洞察

Context Mode 的出现揭示了一个重要趋势：**AI 编程工具的上下文管理正在从"扩大窗口"向"精准过滤"演进**。随着 Claude 3.5/4、GPT-4o 等模型上下文窗口普遍达到 200K tokens，业界开始意识到：单纯扩大窗口不是解法，因为数据污染让大窗口和小窗口一样低效。

Context Mode 的解决思路——**在协议层（MCP）而非应用层做上下文治理**——为整个生态提供了一种可复用的架构范式。未来，类似的输出侧优化可能会成为所有 AI Agent 工具的标准配置。
