这篇论文在说什么？

你有没有发现一个现象：给 LLM 接上工具之后，它变得特别"爱用工具"——哪怕问它"1+1等于几"，它都可能先调一下计算器再回答。

来自 UC San Diego 和 Amazon AWS 的团队研究了这个问题，他们的结论很直接：模型其实心里清楚该不该调工具，只是嘴上说不好。

具体来说，他们做了三件事：

  1. 造了个基准测试叫 When2Tool——18 个环境、3 个难度级别，专门测试"什么时候该用工具"这个决策
  2. 发现现有方法都不行——不管是改提示词还是让它先推理再行动，效果都很粗糙
  3. 提出 Probe&Prefill 方法——从模型的隐藏状态里直接读出"要不要用工具"的信号。结果：减少 48% 的无效工具调用，准确率只掉了 1.7%

*图源：原文 Figure 1 — 基准设计（左）、基线对比（中）、Probe&Prefill 方法（右）*

为什么要关注？

这个问题太真实了。现在几乎所有 AI Agent 产品都接了工具——搜索、计算器、API 调用、数据库查询……但每次工具调用都有成本：

  • API 费用——GPT-4o 每次调用几美分到几十美分不等
  • 延迟开销——多一次网络往返就是多几百毫秒到几秒等待
  • Token 消耗——工具返回的结果要塞进上下文

更麻烦的是，现有的工具调用 benchmark 基本都只测"能不能正确使用工具"，完全不关心"是不是该用工具"。这导致一个问题被长期忽视：模型在能直接回答的问题上乱调工具，白白浪费资源。

这篇论文是第一个系统性研究这个问题的工作，而且给出的方案极其轻量——不需要微调、不需要额外训练模型、推理开销不到 1ms。对任何做 Agent 产品的人来说，这都是实打实的省钱利器。

核心方法

关键思路：模型"心里有数"

整篇论文最核心的发现可以用一句话概括：

工具必要性（要不要调工具）的信息，已经编码在 LLM 生成第一个 token 之前的隐藏状态里了，而且可以被一个简单的线性分类器以 0.89-0.96 的 AUROC 解码出来。

换句话说，模型在还没开口说话的时候就已经"知道"了答案——但它生成的时候不一定按这个知识行动。

他们设计了 When2Tool 基准测试，包含 18 个环境，分为三大类：

类别 核心问题 典型例子
A: 计算规模 我能心算出来吗？ Easy: 20+20 → Hard: 10¹² × 10¹¹
B: 知识边界 我训练数据里有这个吗？ Easy: 法国首都 → Hard: 合成虚构实体查询
C: 执行追踪 我能可靠追踪执行过程吗？ Easy: print(2+3) → Hard: 20次迭代DP追踪

为什么 Prompt-only 和 Reasoning 都不行？

他们先试了两大类朴素方法：

Prompt-only：在提示词里告诉模型"尽量别用工具"。结果简单任务确实少调了，但困难任务也跟着少调——因为模型分不清哪些该省哪些不该省。

Reason-then-Act：让模型先写一段推理分析需不需要工具再决定是否调用。听起来很合理？实际效果很差——特别是在 Llama-3.3-70B 上，Reason-then-Act 让准确率从 83.1% 直接跌到 47.9%。模型推理完了反而更乱了。

*图源：原文 Figure 3 — 不同难度下准确率 vs 工具调用次数，Reason-then-Act（红色）在Hard任务表现糟糕*

Probe&Prefill：从隐藏状态"读心"

既然模型隐藏状态里已经有信号了，为什么不直接读出来？Probe&Prefill 分三步走：

  1. Step 1 提取隐藏状态：对输入跑一次前向传播，取最后一个 token 在所有层的隐藏状态（和获取 KV cache 同步完成）
  2. Step 2 线性探针预测：训练一个带 L2 正则的逻辑回归，输出"需要工具"的概率 p，900 个样本 CPU 秒级训练完
  3. Step 3 预填充引导：根据探针结果塞一句引导句（如 "I can solve this directly without using a tool."），模型顺着引导继续生成

探针到底有多准？

AUROC 0.89-0.96 是什么概念？基本上意味着探针猜得比模型自己说的还准：

效果怎么样？

每次节省一次工具调用，你要付出多少准确率的代价？（数字越接近 0 越好）

方法 Easy 成本比 Medium 成本比 Hard 成本比 Overall 成本比
Necessary (全调用) -3.5 -17.9 -44.4 -16.8
No Tool (禁用工具) -25.2 -36.9 -60.4 -40.5
Prompt-only (最优) ~ -17.3 ~ -24.3 ~ -58.4 ~ -33.3
Probe&Prefill -1.6 -6.2 -3.4 **-3.6**

Probe&Prefill 的 overall 成本比只有 -3.6，最好的 Prompt-only 基线大概 -17——差距接近 5 倍。换个角度说：

  • 想让工具调用减半 → 用 Probe&Prefill 只丢 1.7% 准确率
  • 用其他方法 → 要么减不到一半，要么准确率暴跌

和其他方案比有什么不同？

维度 Prompt 工程 SFT 微调 Reason-then-Act Probe&Prefill
需要训练？ ❌ ✅ 全量微调 ❌ ✅ 仅线性探针
修改权重？ ❌ ✅ ❌ ❌
推理额外开销 ~0 ~0 高 < 1ms
工具调用减少 ~20-30% 不稳定 ~15-25% 48%
准确率损失 高 可能提升 高(Llama崩溃) 1.7%

最大的区别在于：Probe&Prefill 不碰模型本身。它只是在模型外面挂了一个极小的线性探测器，读取模型本来就有的内部信号。即插即用到任何 LLM 上，不影响原有能力，探针可随时更换。

对开发者意味着什么？

能不能用？怎么用？

完全可以，而且非常实用。代码已开源，实现起来也很简单：

  1. 收集约 1000 个标注样本（模型在无工具条件下能否正确答题）
  2. 训练一个逻辑回归探针——CPU 秒级完成
  3. 在你的 Agent pipeline 加一步：输入 → 前向传播 → 探针判断 → 条件性预填充

整个流程和获取 KV cache 完全兼容，不会增加额外的模型前向传播。

适用场景

  • 高频 API 调用的 Agent——客服机器人、代码助手、数据分析 Agent，每省一次都是真金白银
  • 低延迟要求场景——减少不必要的网络往返
  • Token 预算敏感的应用——长对话下工具返回占大量上下文窗口
  • 多步 Agent 流程——多跳任务中减少中间冗余调用

局限性

  • 探针依赖针对自己工具集和任务分布的 ~1000 条标注数据
  • 当前仅在计算/检索/代码执行类工具上验证，多模态工具待验证
  • Soft prefill 在某些模型上可能被忽略（Llama 需要 hard prefill）
  • 仅针对"要不要调工具"决策，不涉及选哪个工具、参数传递等下游问题
