📌 项目背景：非结构化文本的"宝藏"困境

企业最核心的数据往往以最"难用"的形式存在——冗长的临床病历、复杂的法律合同、海量的客服对话记录、不规则的业务报表。这些数据被称为非结构化文本，占据了全球数据的80%以上，却难以被计算机系统直接处理。

传统解决方案有两种：一是基于规则的正则表达式匹配，维护成本高且在面对语序变体时脆弱不堪；二是训练专门的信息提取模型，需要大量标注数据和漫长的训练周期。

2025年7月，Google开源了LangExtract，给出了第三种答案：利用大语言模型（LLM）的语义理解能力，通过少量示例即可定义任意领域的提取任务，并且——这是最关键的创新——每一个提取结果都能精确映射到原文中的字符位置，生成可交互验证的可视化报告。

🚀 核心功能（7大功能深度解析）

🎯 精确原文溯源

内置 WordAligner 组件，将每个 extraction_text 映射到原文 CharInterval，对齐质量分 EXACT/FUZZY/UNALIGNED 三级，让LLM从"黑盒"变"透明盒"

📋 声明式结构化输出

Few-shot提示范式，用户只需提供任务描述+3-5个示例，模型即按结构输出；Gemini等模型支持受控生成，YAML Schema约束解析失败率<0.1%

📄 长文档并行处理

智能分块（max_char_buffer）+ 多线程并发（max_workers=20）+ 多轮提取（extraction_passes=3），14万字符《罗密欧与朱丽叶》全文仅需数分钟

📊 交互式HTML可视化

一行代码生成独立HTML，原文与提取结果并排展示，鼠标悬停自动高亮原文对应位置，满足医疗/法律审计追踪需求

🔌 多LLM后端支持

插件化Provider架构，内置Gemini/OpenAI/Ollama，支持社区扩展；优先级机制解决多Provider匹配冲突，无缝切换云端与本地模型

🌐 跨领域零样本适配

无需微调，修改提示词和示例即可适配新领域；官方示例涵盖文学分析、医疗信息提取、放射报告结构化（RadExtract子项目）

☁️ Vertex AI批量处理

支持接入Google Vertex AI批量推理API，成本比在线推理降低50-70%，适合每天处理数万份文档的企业生产场景

🪜 技术亮点一：五层严格分层架构

LangExtract通过 import-linter 强制执行五层模块边界，防止架构退化。每一层只允许导入更低的层，保证核心抽象的稳定性：

📱 应用层：extraction / io / visualization（面向用户的入口层，可导入所有下层）
🔧 高层服务层：annotation / prompting / resolver / chunking（辅助功能，可被应用层导入，但不可被核心层导入）
⚙️ 服务层：inference（推理协调层，管理LLM调用流程，可导入providers和core）
🔌 提供者层：providers/*（模型适配实现，不能导入inference，可独立演进）
🧱 核心层：core/*（稳定抽象 BaseLanguageModel / Extraction / Tokenizer，不依赖任何上层）

这一架构的核心好处是：Provider层可以独立演进，社区无需修改核心代码即可添加对新模型的支持。目前已有Gemini、OpenAI、Ollama三个官方Provider，以及社区开发的DeepSeek、Claude等第三方Provider。

🔬 技术亮点二：双坐标系溯源机制（核心创新）

溯源的技术实现流程

LLM输出 extraction_text
↓ ① Tokenize（Unicode感知分词，使用 regex 库）
↓ ② 与原文Token序列进行模糊/精确匹配
↓ ③ 映射到 CharInterval（字符级位置）
↓ ④ 输出 AlignmentStatus 质量评级

自动检测"示例泄漏"：如果模型在提取结果中复现了示例中的内容（而非输入文本中的内容），LangExtract会将对应结果的 char_interval 设为 None，并发出 Prompt alignment 警告，提醒用户检查提示词对齐质量。

对齐准确率数据：在清晰印刷文本上，EXACT 对齐率达 96% 以上；手写/OCR文本降至约 82%。这一机制让LangExtract的输出具有可验证性，是满足合规审计要求的关键支撑。

🔌 技术亮点三：Provider插件系统

基于Python entry points的插件注册机制

LangExtract的Provider系统通过 pyproject.toml 中的 entry points 注册，运行时通过 importlib.metadata 自动发现。匹配机制采用正则表达式模式，当多个模式匹配时，优先级数值更高的Provider胜出。

Provider 匹配模式 后端SDK 适用场景
GeminiLanguageModel ^gemini- google-genai（≥1.39.0） 默认推荐，成本与质量平衡
OpenAILanguageModel ^(gpt-|o1-|o3-) openai（≥1.50.0） 已有OpenAI API的用户
OllamaLanguageModel ^[a-z0-9_-]+:[a-z0-9_.-]+$ aiohttp（Ollama HTTP API） 本地部署，隐私敏感场景

这一设计让LangExtract在企业混合部署场景（部分数据上云、部分本地处理）下具有充分的灵活性。

🛠️ 快速上手

① 安装

# 基础安装
pip install langextract

# 包含全部可选依赖（推荐）
pip install "langextract[full]"

# 支持OpenAI后端
pip install "langextract[openai]"

# Docker部署
docker build -t langextract .
docker run --rm -e LANGEXTRACT_API_KEY="your-key" langextract python your_script.py

echo 'LANGEXTRACT_API_KEY=your-key-here' >> .env

③ 最小示例（中文场景）

import langextract as lx
import textwrap

# 定义提取任务
prompt = textwrap.dedent("""\
    从文本中提取人物、情感和关系。
    使用原文精确文本，不要改写。
""")

examples = [
    lx.data.ExampleData(
        text="小王轻轻叹气，决定给小李写一封信。",
        extractions=[
            lx.data.Extraction(
                extraction_class="人物",
                extraction_text="小王",
                attributes={"情感状态": "叹息、犹豫"}
            ),
        ]
    )
]

# 执行提取
result = lx.extract(
    text_or_documents="小李收到信后，脸上露出了久违的笑容。",
    prompt_description=prompt,
    examples=examples,
    model_id="gemini-2.5-flash",
)

# 生成可视化HTML
lx.io.save_annotated_documents([result], output_name="result.jsonl", output_dir=".")
html = lx.visualize("result.jsonl")
with open("visualization.html", "w", encoding="utf-8") as f:
    f.write(html)

⚠️ 常见问题

依赖报错：优先尝试 pip install "langextract[full]" 或使用官方容器镜像
输出不稳定：增加few-shot示例的覆盖度，或开启 extraction_passes>1 提升召回
对齐失败：提示中强调 extraction_text必须取自原文，检查中文标点/空格差异

💡 总结：LLM时代信息提取的新范式

LangExtract代表了LLM时代信息提取的新范式：可追溯、可验证、低门槛。它将LLM的"语义理解"能力与传统NLP的"精确对齐"能力有机结合，填补了现有工具生态的重要空白。

对于需要在生产环境中使用LLM进行信息提取的团队，LangExtract提供的溯源机制和可视化能力，是满足合规审计要求的关键支撑。而其插件化的Provider架构，也为企业在多云/混合部署场景下提供了充分的灵活性。
