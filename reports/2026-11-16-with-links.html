AI 会写代码渲染影片，却听不见自己配的音效

  • 开源协议：MIT（LICENSE 文件实测存在）
  • 形态：CLI + Python API + MCP 服务器，本地 CPU 运行

用 Remotion、HyperFrames 这类工具写代码渲染影片，现在已经不新鲜：coding agent 能把转场、字幕、动效全部代码化。但这条流水线上有一环一直是聋的——agent 听不见自己配的音效。它不知道生成的按键音是「高级的闷响」还是「廉价的咔哒」，听不出音效落点比画面切点晚了 80 毫秒，更判断不出音乐起来的时候人声被压没了。

earshot 补的就是这一环：把声音变成 agent 能读、能推理的结构化证据——一个文件听起来像什么、和某段描述匹配到什么程度、长录音里最好的片段在哪、它到底是真实录音还是代码合成。整条链路本地 CPU 运行，提供 CLI、Python API 和 MCP 服务器三种接入方式。更有意思的是，它不只是「听」，还把「听」接回了「造」：agent 写物理合成配方的代码，渲染出候选音效，再由 earshot 的评分器逐个打分，进化搜索迭代，直到像样为止。听和造在同一个工具里闭环，这是它与一般音频分析工具最反直觉的差异。

项目背景：agent 的世界里没有声音

一个 agent 工作流的典型产物是：写脚本、生成画面、渲染视频。音效这一步通常靠两条老路。一条是从音效库下载素材，靠人挑；另一条是调云端文生音频服务，靠运气。两条路 agent 都没法自我校验——它挑完、生成完，不知道结果对不对。

这不只是体验问题，而是流程断裂。Agent 改了画面节奏，音效同步会不会失效？下载了五个 whoosh，选哪个？配完混音，背景音乐起来后人声还在不在？这些问题此前只有「渲染完发给人听」一种解法，而人是流水线上最贵的环节。更麻烦的是返工成本：一条 60 秒的成片，人耳听一遍要几分钟，发现问题后回给 agent 重新配，再听一遍——每一轮往返都以小时计，而且挑音效这件事本身就没有客观标准，两个评审可能给出相反的意见。

现有工具帮不上忙。ffmpeg 能测 LUFS、峰值这类客观量，但「这个音效像不像机械键盘的深闷敲击」它答不了；云端音频大模型（比如把音频传给 Gemini）能描述，但要联网上传、按次付费，且返回的是自然语言，没有可供 agent 阈值判断的校准分数。earshot 的 README 把这个空位说得很直白：agent 能读图、读文件、读浏览器状态，唯独是聋的。

核心功能

1. describe / match / rank：把声音翻译成校准过的文字

earshot describe enter.ogg 输出的不是模糊形容，而是带 z 分数的判定：0.56 秒短瞬态，起音 3 毫秒，190 毫秒内衰减，「最像单次机械键盘按键（z +5.4）」，次选「软性键帽回弹声（z +3.6）」，外加峰值、亮度等实测数字。z 分数对照一个 322 条描述的校准词表计算，这是 agent 能设阈值做判断的关键——拿到的是统计证据，不是玄学形容。

match 进一步回答「这个文件符不符合描述」，裁决分四档（strong / plausible / weak / no match），并告诉你这个匹配在全词表里大概排第几。rank 把一个文件夹里的候选按描述排序，对应「下载了五个音效选一个」的高频场景。

2. find / realness：在长录音里定位，分辨真假

find 在长录音中找出目标声音的时间窗。README 的验证：一段含 17 次单次按键的录音，找出的修剪窗全部落在真实按键上；300 秒场景中每个植入事件都被找到。realness 则判断一段音频是真实录音还是代码合成，held-out 集 ROC-AUC 0.92（整个声音家族被整体留出的口径），逐窗口给出证据。后者对音效库的「挂羊头卖狗肉」检测是个实用场景。

3. timeline / sheet / critique：给整条影片的音轨做体检

timeline 生成逐秒「听觉转写」：事件时间戳、响度、标签，绑定视频后还输出音画同步信息——音效落点相对画面切点的偏差直接可见。sheet 把这些画成一张带频谱、波形、事件标注的 PNG，给读图的 agent 用。critique 是压轴：对照 7 部专业 launch film 建立的评估档，输出「21/23 项指标在范围内，优先修复：1.01 秒前没有任何声音达到 body 响度」这样的带时间戳修复清单。60–90 秒影片在笔记本 CPU 上约 1.5 分钟跑完。

4. forge：写配方造声音，靠听来迭代

这是最不常规的部分。音效不是采样，是物理合成代码：模态谐振器、接触激励、滤波噪声、算出来的房间响应和麦克风，配方里没有一段真实录音。渲染出一批候选后，earshot 内建的 critic 打分——描述匹配、真实感、与参考录音的距离，再加一组不依赖模型的惩罚项（1/3 倍频程音色平衡、谱时包络、咔哒/混叠/削波等伪声）。便宜的预筛先按测量值海选，模型只听决赛圈，进化搜索保留最优并变异。README 明确警告了 Goodhart 定律（Goodhart's law）：forge 可以「讨好」自己的模型而声音没变好，所以要相信测量值、频谱图和人耳终审。

5. fit / sfx / kit：逆向配方与即取即用的音效库

fit 反方向走：把一段真实录音拟合成可编辑的配方代码，可以改参数、做声音插值。README 给的测量：12 条真实录音上，配方重渲染与原录音的 CLAP 余弦中位数 0.945。sfx/kit 则是内置的 252 个纯代码音效银行，按 id 渲染、不用模型不用网络，launch 预设把每个音效按角色对齐音乐床和画面切点。

技术亮点

1. 校准词表，而不是模型裸输出

多数「AI 听音频」方案直接暴露模型的自然语言输出，agent 没法稳定地做判断。earshot 的做法是先建 322 条描述的词表，再对每条描述做统计校准，所有匹配都换算成 z 分数并给出最近混淆项。代价是词表覆盖有限、超出词表的表达会失真——README 没有回避这一点，docs/LIMITS.md 明确写了哪些判定可信、哪些只能当提示。

2. 验证文化：每个数字都能溯源到命令

README 里每个性能数字后面都跟着测量它的命令，统一收在 docs/VALIDATION.md，评测脚本和结果在 eval/ 目录。125 条留出集测描述匹配（strong 裁决类别正确率 98%、精确变体 61%）、真实感分类 ROC-AUC 0.92、混音事件检出率 93%（安静音效在音乐下是 89%）。仓库不存任何音频和视频，评测数据因为有授权不随库分发，只提交派生数字。这种做法在个人开发者的仓库里少见，crazycoderslab 的实测文章专门称赞了 README「对局限异常诚实」。

3. CPU-only 的取舍

双模型（CLAP 的 laion/larger_clap_general 加一个 AudioSet 标签模型）全程 CPU 推理，不上 GPU。代价是单次 CLI 调用要重载模型 20–40 秒；README 的对策是 MCP 服务器长驻（模型保温）或一个 Python 脚本内循环调用。对「嵌入 agent 工作流、不是实时处理」的目标场景，这个取舍成立。顺带一提，项目附带的两个 agent skill 也值得看：skills/earshot 教 agent 什么时候该用哪条命令、什么时候不该信裁决；skills/real-sound 是一套从授权素材采购、音乐剪辑、JSON 音效设计、确定性混音到母带处理的完整流程文档。把「怎么用」本身做成 skill 交付，比单独一份 README 更贴近 agent 的消费方式。

适用人群

  • 用 Remotion / HyperFrames 等代码渲染影片的开发者：音效选料、音画同步检查、混音质检全部交给 agent，省掉渲染完人耳听一遍的往返。
  • 独立游戏开发者：forge/sfx 用代码生成可控参数的 UI 音效，不用翻音效库，也没有授权纠纷（仍需读 issue #21 的讨论，见下文局限）。
  • agent 工具链作者：MCP 服务器 + 两个现成 agent skill（earshot 和 real-sound），接进 Claude Code 几条命令的事。
  • 做产品发布视频的小团队：critique 对照专业 launch film 的评分卡，低成本拿到一份「先修什么」的清单。
  • 声音设计学习者：fit 把录音反向拆成物理合成配方，是现成的教学材料。

快速上手

前置依赖：Python 3.10+、uv、ffmpeg/ffprobe 在 PATH 中。纯 CPU，无 GPU 要求。README 给的推荐安装：

uv tool install "earshot[mcp] @ git+https://github.com/Leonxlnx/earshot"
earshot doctor --fetch     # 预下载两个模型，约 1.1 GB（README 口径）

三个不需要模型的命令可以先试：

earshot sfx list --kind whoosh
earshot sfx render whoosh_fast/crisp -o w.wav --dur 0.8 --apex 0.32
earshot describe w.wav

接进 Claude Code 作为 MCP 服务器（路径按实际替换）：

claude mcp add earshot --scope user -e EARSHOT_THREADS=3 -- /path/to/earshot/.venv/bin/python -m earshot mcp

常见坑：一是单次 CLI 调用重载模型 20–40 秒，批量任务务必走 MCP 或 Python API；二是共享机器上用 EARSHOT_THREADS=2~3 限线程；三是 forge 的参考录音集有授权、不随库分发，自己的录音用 --refs 接入；四是 fit 的产物是原录音的衍生物，配方的授权跟着原录音走。

对比分析

维度earshot云端音频大模型（如 Gemini 音频理解）ffmpeg / pyloudnorm 等测量工具
部署形态本地 CPU，装完离线可用云端 API，音频需上传本地 CLI/库
输出校准 z 分数 + 裁决 + 带时间戳修复项自然语言描述客观物理量（LUFS/峰值/频谱）
agent 可判定性强（阈值化、分档裁决）弱（需二次解析）中（量对但缺语义）
声音生成物理合成配方，可迭代、可参数化部分支持文生音频，黑盒无
成本一次性 1.1 GB 模型下载按调用计费免费
局限/风险Alpha 阶段（v0.4.1），盲测样本小，词表外失真，商用授权待明确隐私与成本，输出不稳定听不懂语义

它同样不解决「好不好听」的主观问题——README 原话说它不能判品味与情感（taste or emotion），critique 的评分卡描述的是那 7 部参考影片的风格，不是所有好影片的标准。工程上的真实边界是：单次暴露的干净音效判定可信，混音中密集事件的标签只能当提示，模型对 14 kHz 以上的频段无能为力。

点评：earshot 的适用边界很清楚——它做「效果音与音轨质检」，不做语音转写、不做音乐生成、不判品味；如果你的需求是给视频配一段背景音乐或配音，它是错的工具。反过来说，只要流程里存在「agent 产出的东西需要被听见」这一环，它目前几乎没有同位竞品。

局限

把负面的信息单独列出来，这几条在决定要不要上生产前都值得读完：

  1. Alpha 阶段，验证样本小。 版本停在 v0.4.1，README 自己标注 package 处于 Alpha；盲测是一位听众的小样本，launch scorecard 也不是盲测（首轮跑完后改过规则，基线 71% 对 86%）。crazycoderslab 实测承认没有测 forge、critique 和 MCP 服务器三块。
  2. forge 有讨好自己模型的动机。 README 主动引用 Goodhart 定律：合成器可以拉高自家 critic 的分数而音质没变好，官方建议以测量值、频谱图和人耳终审为准。这不是缺点被藏着，而是这条回路的结构性风险。
  3. 商用授权有未决问题。 issue #21（2026-11-08 开，未关闭）问的正是渲染出的音效 bank 音频能否用在商业视频里；fit 的产物被视为原录音的衍生物，授权跟着原录音走。生产环境使用前需要自己确认。
  4. Windows 细节坑。 issue #23（2026-11-10 开，修复 PR 已合但原 issue 仍开放）：Windows PowerShell 写出的带 BOM 的 JSON（cue/kit/params）会加载失败。
  5. 感知上限明确。 分不清品味与情感，读不出语音内容，模型覆盖不到 14 kHz 以上频段；混音中密集事件的标签只是提示。单次 CLI 调用重载模型 20–40 秒，高频使用必须走 MCP 或 Python API。
  6. 社区还薄。 截至 2026-11-16，watchers 9 人，issue 评论区几乎为 0；星标曲线 500（2026-10-17，aifrontierpost）→ 3,047（toolsdepth 评测时点，原文未注明日期）→ 4,920（2026-11-16，GitHub API）。增速快但生态未成型，遇到坑大概率要自己读源码。

写在最后

第一，earshot 真正立住的不是「又一个音频工具」，而是一种可复用的工程模式：把人类感官通道翻译成带校准的证据（z 分数、ROC、逐窗证据），再让生成与评判在同一闭环里互锁。多模态 agent 的下一批工具大概率会照这个模板长出来——触觉、布局感、时间感，都可以问同一个问题：agent 怎么校验自己造出来的东西。

第二，行动建议：如果你的工作流里有代码渲染的影片或程序化音效，值得花 30 分钟装上跑一遍 critique；把它接进 MCP 的收益大于单次使用。同时把它当 Alpha 对待——盲测是一位听众的小样本，商用音效的授权边界（issue #21，2026-11-08 开）还挂着，生产环境用之前自己验一遍。
