这篇论文在说什么？

想象一下：你部署了一个 AI Agent 帮团队处理日常任务，用了两个月，它每次遇到同样的坑还是会掉进去。你只能等下一次人工更新才能修——这就是现在所有 AI Agent 系统的真实处境。

中科大和港科大的团队决定不走这条路。他们搞了一个叫 MOSS 的系统，让 AI Agent 部署后能自己改自己的源代码——不是改提示词、不是改技能配置，而是直接修改 agent 框架本身的核心代码（路由、状态管理、钩子顺序这些）。一次自动进化，四个任务的平均分从 0.25 暴拉到 0.61，直接翻倍还多。

*图源：原文 Fig.1 — MOSS系统拓扑架构*

为什么要关注？

现在的"自我进化"Agent 其实都在玩文字游戏。Voyager、SkillClaw、EvoAgentX 这些系统所谓的"进化"，本质上就是让 Agent 改改技能描述文件、调调提示词——全在"文本层"打转。

问题在哪？Agent 框架的核心代码从来没被碰过。 路由逻辑、钩子顺序、状态不变量、任务分发——这些东西活在代码里，不在任何文本文件里。一旦故障出在这层，改多少提示词都没用。

"Once a failure originates in this layer—mis-routed messages, hooks firing out of order, corrupted session state, atomicity bugs across concurrent skills—no update to skills, prompts, or memory can reach it: the bug is not in the prompt text, and a prompt rewrite cannot paper over it."

— 论文原文，Introduction 第2段

翻译一下：如果 bug 出在框架代码层，你改提示词就是在隔靴搔痒。而且这个问题会越来越严重——随着 Agent 系统越来越复杂，框架层的代码也在膨胀，这类"不可达"故障的比例只会越来越高。MOSS 的思路很直接——让 Agent 自己去改代码。

核心方法

关键思路

MOSS 做了一件很反直觉的事：它让一个 AI 系统去修改另一个 AI 系统的源代码，然后自动验证、自动部署。

你可能会想：这不怕改崩了吗？MOSS 的设计恰好围绕"安全"做了层层关卡。它的进化流程有四个嵌套层级：

*图源：原文 Fig.2 — MOSS进化的四个嵌套层级*

最外层（Layer 0）是进化前的基线状态。Layer 1 是迭代循环——跑完一轮，评估效果，不行再来。Layer 2 是核心：一个 7 阶段的确定性流水线。Layer 3 是阶段内的重试机制——每一关不过，就再试。

这 7 个阶段依次是：Locate（定位故障） → Plan（制定方案） → Plan-Review（方案审查） → Implement（执行修改） → Code-Review（代码审查） → Task-Evaluate（验证修复） → Verdict（裁决是否接受）。

技术细节

有两个设计特别值得展开说：

第一，MOSS 不是"随便改"——它只改被故障证据锚定的位置。 每次进化都基于一个自动收集的"生产故障证据包"。Agent 在线上运行时，失败的 case 会被记录并打包。MOSS 只能围绕这些证据做修改——不能心血来潮重构整个代码库。这就好比医生做手术，只能动病灶，不能顺便割个阑尾。

第二，部署采用了"热替换 + 健康检查 + 自动回滚"的容器化方案。 验证通过的代码会被打包成新的容器镜像，然后原地替换旧容器。替换后，一个健康探针持续监控心跳。新版本出问题就自动回滚。整个过程只需要用户的一次确认。

"Candidates are verified by replaying the batch against the candidate image in ephemeral trial workers, then promoted via user-consent-gated, in-place container swap with health-probe-gated rollback."

— 论文原文，关于部署安全机制

这个部署方案的设计相当工业级——考虑到了验证、用户同意、健康检查、自动回滚每一步，不像是实验室玩具，更像是给生产环境准备的。

效果怎么样？

MOSS 在一个真实的生产级 Agent 平台 OpenClaw 上做了验证，底层模型用的是 DeepSeek V3.2。四个运营/合规审计类任务，单次进化后的结果：

任务 基线分数 进化后 提升
SLA合规审计（中文） 0.327 0.533 +0.206
SLA合规审计（英文） 0.253 0.545 +0.293
补货链检查（中文） 0.221 0.457 +0.235
补货链检查（英文） 0.209 0.905 +0.696
四任务平均 0.253 0.610 +0.357

数据来源：原文 Table 2

几个有意思的发现：

1. 英文任务提升远大于中文任务。 补货链检查英文版从 0.21 直接飞到 0.90（三次测试全部超 0.75 及格线），而中文版只到了 0.46。可能原因是 DeepSeek V3.2 和 OpenClaw 的底层提示/工具链对英文支持更好。

2. SLA 类任务提升稳健但不惊艳（+0.2~0.3）。这类任务涉及时间差计算和分级归类，属于"改了工具链但还是有认知难度"的类型。

3. 进化只改了 3 个文件，177 行新增、1 行删除。 改动量极小但效果巨大——正好印证了论文的核心论点：很多故障的根因在框架代码层，改一点点就能修复一大片。

和其他方案比有什么不同？

前面提到市面上已经有不少"自我进化"Agent 系统了，但它们都在文本层操作。来看看差异：

系统 改技能 改提示词 改记忆 改框架代码
Hermes Agent ✅ ❌ ✅ ❌
SkillClaw ✅ ❌ ❌ ❌
GenericAgent ✅ ❌ ✅ ❌
EvoAgentX ✅ ✅ ❌ ❌
MOSS ✅ ✅ ✅ ✅

数据来源：原文 Table 1

这不是"做得更多"的差别，而是质的区别。前面那些系统的进化空间是有限的——无论怎么改提示词和技能描述，框架代码里的路由 bug、状态竞争、钩子顺序错误永远碰不到。MOSS 把进化空间从有限扩展到了图灵完备——因为编程语言是图灵完备的，而源代码改写可以产生任意程序结构。

此外，MOSS 还有一个其他系统没有的特点：确定性。改代码的效果是确定的——路由逻辑变成代码后，每次都按同样的规则执行。而改提示词的效果取决于模型当天的"心情"——模型能力波动、上下文窗口竞争、注意力稀释，都会让提示词的生效程度打折扣。

对开发者意味着什么？

说实话，MOSS 现在离"开箱即用"还有距离。它依赖 OpenClaw 这个特定的 Agent 平台，流水线的很多环节需要适配自己的基础设施。但如果你的团队已经在用类似 OpenClaw 的生产级 Agent 框架，MOSS 提供了一个很清晰的进化方向：

第一，故障驱动的自动修复。 与其每次出了问题手动排查 → 改代码 → 测试 → 部署，不如让系统自己完成这个循环。MOSS 的模式是"收集故障证据 → 定位根因 → 自动修复 → 自动验证 → 一键部署"——人工只需要在最后点一下确认。

第二，代码层的自我进化比文本层有效得多。 如果你的 Agent 系统经常出一些"改提示词没用"的 bug（比如工具调用顺序错、状态丢失、并发冲突），那大概率是框架代码的问题。MOSS 的源代码级改写就是针对这类问题的。

第三，安全机制值得借鉴。 即使你不用 MOSS 本身，它的"编码权与控制权分离"（外部编码 Agent + MOSS 裁决）、"故障证据锚定修改范围"、"容器热替换 + 健康检查 + 回滚"这些设计，都是 Agent 系统自修改时必要的安全护栏。

最后说一句：MOSS 目前只在 4 个任务上做了验证，开源代码也比较早期。但它的思路是对的——当 AI Agent 越来越复杂，人工维护越来越跟不上时，自我进化就不是"锦上添花"，而是"不这么做就活不下去"了。
