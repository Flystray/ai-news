# 1M 参数的 OCR 跑在 CPU 上，比 Tesseract 快 15 倍

> GitHub AI 项目日报 · 2026-11-10 · 公众号「fly的AI学习」

## 项目速览

- **项目地址**：[datalab-to/indra](https://github.com/datalab-to/indra)
- **Star/Fork**：⭐ 1,725 · 🍴 176（截至 2026-11-10，创建于 2026-10-13）
- **主要语言**：Python（推理走 ONNX Runtime，不用 PyTorch）
- **开源协议**：代码 Apache-2.0，模型权重为修改版 OpenRAIL-M
- **形态**：CLI + Python 库 + 本地 Web 查看器
- **文档**：README 为主；模型托管在 [Hugging Face](https://huggingface.co/datalab-to/indra-ocr)，另有官方 Playground

Indra OCR 是 Datalab 在 10 月 13 日开源的文档识别引擎，主识别器 rec.onnx 只有约 125 万参数，全部默认模型加起来 730 万参数、76 MB，纯 CPU 跑。它把 PDF 和图片直接转成 Markdown、纯文本或带坐标的 JSON，自带版面分析和阅读顺序。最反直觉的一点：一个百万参数级的模型，在 Datalab 自己的 OmniParseBench 上拿到 66.7，比百度 PaddleOCR 的完整文档流水线 PP-StructureV3（58.4）还高，而单页耗时是后者的约两百分之一。

## 项目背景：OCR 被切成了两半，中间那块一直没人做

做文档处理的人都熟悉这个局面：一头是 Tesseract 这种老牌引擎，免费、本地、不要 GPU，但只给你一行行文字，版面、表格、阅读顺序全得自己拼；另一头是 PaddleOCR 的 PP-StructureV3、DeepSeek OCR、Chandra 这类大流水线，版面表格都能出，代价是 GPU 或者几万毫秒一页。

中间那一段需求一直存在：手上是几万页扫描件、发票、合同、旧档案，机器只有 CPU，希望一次性拿到能直接喂给 RAG 的 Markdown。这类活儿在过去要么忍受 Tesseract 的排版混乱，要么掏 GPU 的钱，要么把它们送去云端 API——后者对法务、医疗、政企基本不可行。

Datalab 这家公司在文档圈不算新人，Marker（PDF 转 Markdown）和 Surya（OCR 与版面分析）都出自他们，创始人 Vik Paruchuri 之前做的是 DataQuest。Indra 是他们产品线里最小、最快的那一档，往上还有跑在托管平台上的旗舰模型 Chandra。

README 里给了几组对比数字（均为 Datalab 自测）：

| 引擎 | 综合分 | 文本分 | 表格分 | 版面分 | 单页中位耗时 |
|------|--------|--------|--------|--------|--------------|
| Indra OCR（auto） | 66.7 | 46.7 | **61.1** | **92.2** | **212 ms** |
| Indra OCR `--math` | **71.4** | **62.7** | 59.6 | 92.0 | 357 ms |
| PaddleOCR PP-StructureV3 | 58.4 | 55.6 | 47.8 | 71.7 | 40,958 ms |
| PaddleOCR PP-OCRv6 small（仅文本模型） | – | 35.8 | 0.0 | – | 2,685 ms |
| Tesseract 5 | – | 19.3 | 0.0 | – | 5,496 ms |

（README 自述，x86、4 vCPU、单页串行、同一批 2,937 页测试集）

这张表里最值得看的是时间那一列。PP-StructureV3 是 40 秒一页，Indra 是 0.2 秒。README 自己标了个注释：PP-StructureV3 有一组分片在首页上卡了 6 小时，所以它的行里少了 19 页——这种细节反而是可信度的一部分。

项目上线第一周，Hacker News 上出现了一条 "Indra OCR: a 1M-parameter OCR model that reads 49 pages per second on CPU"，39 个点，讨论不算炸，但持续有人跟。GitNova 的 star 曲线记录显示它 16 天涨到 1,436 星，日增最高 190，被判定为"增长有机"。到 11 月 10 日，仓库是 1,725 星、176 个 fork——fork 与 star 的比例接近 1:10，说明确实有人在拿去跑，而不只是点个收藏。

## 核心功能

### 1. auto 模式：能读文字层就绝不 OCR

大部分 PDF 是数字生成的，本来就有文字层。硬做 OCR 是浪费，直接抄文字层又常常出错——字符编码错乱、连字符断裂、双栏被拉成一行。

Indra 的默认 `--mode auto` 会先对文字层做一轮检查，通过就直接用；不通过才渲染成图去 OCR；文字层页面上嵌在图片里的字，还会单独补 OCR（`hybrid`）。每页的 `source` 字段会告诉你它走了哪条路：`text`、`ocr`、`hybrid` 还是 `error`。

```shell
indra-ocr paper.pdf --mode auto        # 默认
indra-ocr paper.pdf --mode ocr         # 忽略文字层，全页 OCR
indra-ocr paper.pdf --mode text        # 强制用文字层
```

对混合档案（一部分是电子件、一部分是扫描件）来说，这一条省下的时间比模型提速还多。

### 2. 四个识别器 + 一个行级分类器

多语言 OCR 常见的做法是训一个大字符集模型，或者给每种语言配一个模型再手动切。Indra 走的是第三条：四个识别器按脚本分组，一个分类器逐行判断该交给谁。

- `rec.onnx`：拉丁字母（约 50 种语言）、西里尔、希腊，以及拉丁手写
- `rec_cjk.onnx`：中文简繁、日文假名与汉字、韩文
- `rec_rtl.onnx`：阿拉伯、波斯、乌尔都、普什图、库尔德、希伯来
- `rec_world.onnx`：天城文（印地、马拉地、尼泊尔）、孟加拉、泰米尔、泰卢固、卡纳达、马拉雅拉姆、古吉拉特、果鲁穆奇、奥里亚、泰、老挝、高棉、缅甸、僧伽罗、格鲁吉亚、亚美尼亚、埃塞俄比亚

分类器不确定的行，主识别器也会读一遍，谁置信度高用谁的。README 说在 95 种语言的留出印刷页上测过，83 种字符级 F1 ≥ 0.90，67 种 ≥ 0.95。

值得注意的是它连竖排也处理了。中文、日文竖排版面会先转 90 度当横向读，读完把坐标映射回原页面，`page.vertical` 标记为真。中文里有 11,749 个常用加生僻汉字在识别范围内——这个数字来自一位把 Indra 移植到 RK3566 嵌入式板子上的中文开发者，他给出的 `rec.onnx` 体积是 9.7 MB、`det.onnx` 只有 389 KB。

### 3. 版面：给每一行一个框、一个标签、一个顺序

输出的不只是文字。每页有 `blocks`（版面块，按阅读顺序）和 `lines`（行级框 + 置信度）。块标签一共十种：`Text`、`Section-Header`、`Page-Header`、`Page-Footer`、`List-Group`、`Table`、`Caption`、`Footnote`、`Table-Of-Contents`、`Form`。

页眉页脚默认丢掉（`--keep-furniture` 可保留），标题渲染成 `##`，列表渲染成列表，表格渲染成 HTML 表格。这些细节决定了输出能不能直接进向量库，而不是还要写一堆正则清理。

### 4. 全套模型 76 MB，不装 PyTorch

主识别器 1.25M 参数，默认全套 7.3M 参数、76 MB（30 MB 网络 + 46 MB 语言模型）。首跑从 Hugging Face 下载并缓存，离线环境可以用 `--model-dir` 或 `INDRA_OCR_MODEL_DIR` 指本地目录。

依赖只有 ONNX Runtime、OpenCV、pypdfium2。不装 PyTorch，不需要显卡，Python 3.10 起，Linux x86_64/aarch64 和 macOS Apple Silicon 都测过。

### 5. 本地查看器：一页一页对着看

```shell
indra-ocr-viewer --port 8765
```

打开后拖进 PDF 或图片，页面会在原图上叠加行框、版面块、阅读顺序，旁边并排给出渲染后的 Markdown、原始 Markdown、逐行置信度、JSON 输出和各阶段耗时。装上 `indra-ocr[tesseract]` 还能左右对比 Tesseract 的结果。文件不出本机。

对决定"要不要换掉现有 OCR"这件事来说，这个 viewer 比任何 benchmark 都实用——用自己的文档跑一遍，好坏立刻清楚。

## 技术亮点

### 1. 不确定的行，用 n-gram 语言模型重新投票

CTC 识别器是贪心解码，一步取一个最优类。遇到模糊的字，贪心很容易把 `rn` 读成 `m`、把 `l` 读成 `1`。

Indra 的做法是给置信度低于阈值的行开一条后路：CTC 前缀 beam search 保留多个候选读数，再用一个 n-gram 语言模型打分，`score = log P_ctc + alpha * log P_lm + beta * tokens`。识别器自己的概率仍占主导，所以生僻但写清楚的词不会被语言模型"纠正"掉。

那 46 MB 的"语言模型"就是给这条后路备的——每个脚本组一份回退表。这也是为什么模型从 0.3 版的 18 MB 涨到 1.1 版的 76 MB，速度也从 49 页/秒掉到 44 页/秒。用一点速度和体积换准确率，这个取舍在文档场景里是划算的。

### 2. 不靠 GPU，靠一核一进程

32 核上 43.9 页/秒，4 核 6.2 页/秒，基本线性。实现方式是每个核起一个单线程 worker 进程、一页一个任务——ONNX Runtime 的 session 不支持并发 Run，所以并行来自进程而不是线程。

代价是内存随核数线性涨，且 Windows/macOS 上必须写 `if __name__ == "__main__":` 守卫，否则 worker 会重复导入主模块。README 把这个坑写在了示例代码的注释里，属于少见的诚实。

### 3. 顺手造了个基准：OmniParseBench

各家 OCR 的"准确率"基本没法比——测试集不同、评分口径不同、有的只测文本不测版面。Datalab 干脆自己造了一个：16,288 条通过/失败测试，2,937 页，分文本、表格、版面三个族，综合分取三者均值。基准和评分器一起开源在 [omni_parse_bench](https://github.com/datalab-to/omni_parse_bench)，README 里给了完整的复现命令：

```shell
python bench/opb_indra.py --out runs/opb_auto --mode auto --procs 8
```

自己造基准再给自己打分，天然有利益冲突。但它的价值在于把"综合分 66.7"拆成了可核对的 16,288 个单项，任何人都能拿同一批评测去质问某个数字。对第三方移植者来说这也是刚需——那个 Go 版本的作者就是照这份基准逐项对齐的。

### 4. 生态已经长出来了

判断一个工具能不能长期用，看有没有人愿意为它重写一遍。Indra 发布不到一个月，已经出现了一个完整的原生 Go 移植 `praktiskt/indra-ocr-go`（v0.35.0），把检测、识别、阅读顺序、RTL 重排、beam search 全部重写，模型和 ORT 库直接嵌进二进制，linux/amd64 上零依赖、零下载、零落盘。同一份基准、同一个 HF 模型目录，两边分数能对上，这种一致性只有在规范写得足够清楚时才做得到。

中文社区那边，有人把它接进了 RK3566 开发板的 OCR 项目，和 PP-OCRv5 的 NCNN 版本并列做多引擎。他的笔记里提到一个有意思的判断：Indra 的价值不在中文主力场景，而在生僻字、多语言混排这类 PP-OCR 覆盖不足的边角。

## 适用人群

- **做 RAG 的工程师**：手里有几千上万页 PDF，需要先变成带标题层级的 Markdown。`--out` 一条命令批量跑完，输出可直接切块入库。
- **法务、审计、档案数字化**：数据不能出内网，机器只有 CPU。76 MB 模型 + ONNX Runtime，笔记本和 ARM 服务器都能跑，完全离线。
- **多语言内容团队**：需要处理阿拉伯语、印地语、泰语、高棉语这类小语种扫描件，过去只能上云或者人工录入。
- **嵌入式 / 边缘设备开发者**：`det.onnx` 389 KB、`rec.onnx` 9.7 MB，已经有中文开发者在 RK3566 这类板子上跑通。
- **想换掉 Tesseract 的老系统**：viewer 支持左右对比，先用自己的一批文档看差距，再决定是否迁移。

## 快速上手

```shell
# 1. 安装（Python >= 3.10）
pip install indra-ocr

# 2. 最小可用：一页 PDF → 标准输出 Markdown
indra-ocr paper.pdf

# 3. 批量：每个输入一个 .md
indra-ocr *.pdf --out results/

# 4. 要结构化数据（行、框、版面块、置信度）
indra-ocr scan.png --format json

# 5. 表格多的文档，开公式识别（慢一些，但文本分从 46.7 涨到 62.7）
indra-ocr paper.pdf --math

# 6. 本地查看器
indra-ocr-viewer --port 8765
```

Python 侧：

```python
import indra_ocr

conv = indra_ocr.load(threads=4)          # mode="auto" | "ocr" | "text"
for i, page in conv.convert("paper.pdf"):
    print(page.source, page.timings["total_ms"])
    print(page.markdown)
    print(page.blocks)                     # [{"label", "bbox", "text"}] 按阅读顺序
```

几个已知的坑：

1. 首跑要下 76 MB 模型，内网环境务必提前备好目录并设 `INDRA_OCR_MODEL_DIR`。
2. `convert_many` 在多进程模型下必须写 `if __name__ == "__main__":`，否则 macOS/Windows 会出问题。
3. `--dpi` 默认 200。超过 1 亿像素的页面会被降采样，小字会丢。
4. CLI 遇到读不了的文件不会中断，最后以退出码 1 结束，脚本里记得判返回值。

## 对比分析

| 维度 | Indra OCR | PaddleOCR PP-StructureV3 | Tesseract 5 |
|------|-----------|--------------------------|-------------|
| 综合分（OmniParseBench） | 66.7（`--math` 71.4） | 58.4 | 仅文本 19.3 |
| 文本分 | 46.7（`--math` 62.7） | **55.6** | 19.3 |
| 表格 / 版面 | **61.1 / 92.2** | 47.8 / 71.7 | 不输出 |
| 单页耗时（4 vCPU） | **212 ms** | 40,958 ms | 5,496 ms |
| 硬件要求 | CPU 即可 | 建议 GPU | CPU |
| 中文场景 | 64.0，弱于 PP-OCRv5（65.4） | **68.4** | 一般 |
| 手写 | 25.2%，勉强 | 未单独评测 | 差 |
| 许可 | 代码 Apache-2.0，权重 OpenRAIL-M 有商用限制 | Apache-2.0 | Apache-2.0 |
| 局限 / 风险 | 复杂表格、手写、退化扫描件都差；中文不是它的强项；权重许可禁止与 Datalab API 竞争 | 慢两个数量级，CPU 上基本不可用 | 无版面，输出还要大量后处理 |

表格后面得说清边界：**如果你的文档以中文为主，Indra 现在并不是最优解**。README 自己给了数字——136 条中文测试里 Indra 64.0，PaddleOCR 的 PP-OCRv5 移动端中文模型 65.4，PP-StructureV3 68.4。多语言混排、英文为主、追求吞吐量的场景，它才是划算的那个。

## 写在最后

这个项目真正改变的不是"OCR 准确率又高了几个点"，而是把"高质量文档解析"的硬件门槛从一张显卡拉到了一台没有显卡的服务器。过去 40 秒一页的东西现在 0.2 秒一页，意味着 1 万页的批处理从 4 天变成 35 分钟——很多原本因为成本被砍掉的数字化项目，现在能重新拿出来算账。

但它也不是通用答案。手写 25.2%、退化扫描件 29.5%、复杂表格会串行串列，中文分还不如 PaddleOCR。README 自己列了 8 条局限，这在开源项目里算相当坦诚。

如果要动手，建议按这个顺序：先 `pip install indra-ocr`，用 `indra-ocr-viewer` 拿自己最刁钻的 50 页跑一遍，和现有方案并排看；确认能用，再上批量。别先看 benchmark 就替换生产管线。
