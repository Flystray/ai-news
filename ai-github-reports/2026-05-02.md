## 一、项目背景：为什么 LiteRT-LM 值得关注？

2026 年，端侧 AI 的拐点已经到来。

过去两年，大模型的主流部署方式一直是"云端 API"——把用户的 prompt 发到远程服务器，等几百毫秒再拿回结果。这套模式有三大结构性困境：**网络延迟不可控**（100–500ms 起步）、**数据隐私难保障**（所有输入都离开设备）、**成本随用量线性累积**。

与此同时，硬件在飞速进步。2025–2026 年发布的旗舰芯片，NPU 算力已经突破 40 TOPS：高通骁龙 X Elite（45 TOPS）、Apple M4（38 TOPS）、联发科天玑 9400+、Intel Lunar Lake NPU（48 TOPS）相继落地。硬件已经就位，缺的是能真正把这些算力用起来的软件框架。

LiteRT-LM 就是在这个背景下诞生的。它是 Google AI Edge 团队推出的**生产级、开源、跨平台 LLM 推理框架**，也是 TensorFlow Lite 的直接继承者——但这次，它是为大型语言模型从底层重新设计的。

TensorFlow Lite 的架构是为 CNN、RNN 等小模型（<100MB）设计的：静态计算图、批量推理、无 KV Cache 支持。这些设计在 LLM 时代全部成为瓶颈。LiteRT-LM 用一套全新的 LLM 原生架构取而代之：支持动态长度序列、自回归推理、KV Cache 原生支持、流式 token 生成——这些都是 Transformer 推理的基本需求，也是 TensorFlow Lite 从未考虑过的问题。

更重要的是，LiteRT-LM 不是实验室项目。它已经集成到 Google 的多条产品线中：Chrome 浏览器（端侧 AI 功能）、Chromebook Plus、Pixel Watch，在**数百万真实设备**上经过生产验证。这是目前开源社区里，少数几个真正"生产就绪"的端侧 LLM 框架之一。

## 二、核心功能（10 项）

### 1. 跨平台推理支持
覆盖从数据中心到指尖的全场景：
- **Android**（稳定）：手机、平板、Android Auto、车载系统
- **iOS**（开发中）：iPhone、iPad，Swift API 即将发布
- **Web**（稳定）：通过 Wasm/WebGL，浏览器里直接跑 LLM
- **桌面端**（稳定）：Linux / macOS / Windows（WSL）
- **IoT**（稳定）：Raspberry Pi 等 ARM 嵌入式设备

### 2. 多级硬件加速
- **GPU 加速**：高通 Adreno、ARM Mali、Apple GPU 全支持
- **NPU 加速**：高通 Hexagon、Apple Neural Engine、联发科 NPU
- **CPU 优化**：ARM NEON、SIMD 指令集深度优化

### 3. 多模态能力
不仅支持文本，还能理解图片、图表、文档（Gemma Vision、Qwen2-VL），以及语音音频流（Gemma 3n 语音模型）。一套框架覆盖三种模态，无需拼接多个工具链。

### 4. 原生工具调用（Tool Use / Function Calling）
这是 LiteRT-LM 的杀手级特性。原生支持函数调用、结构化 JSON 输出、LGuidance 语法约束，以及检索增强生成（RAG）的内置支持。Agentic Workflow 可以直接在端侧运行，不需要云端协调。

### 5. 四级量化体系
| 精度 | 内存占用（7B 模型） | 精度损失 | 适用场景 |
|------|---------------------|---------|---------|
| FP16 | 14GB | 无 | 桌面端、服务器 |
| INT8 | 7GB | <1% | 桌面端、高端手机 |
| **INT4** | **3.5GB** | **3–8%** | **手机、嵌入式** |
| INT2 | 1.75GB | 较大 | 极致受限场景 |

支持 GPTQ、AWQ 等先进量化算法，量化后的模型仍保持可用精度。

### 6. KV Cache 量化与分页管理
KV Cache 是 LLM 推理中内存占用最大的部分之一。LiteRT-LM 支持 KV Cache 的 INT8 量化，并实现了类操作系统的**分页 KV Cache（Paged KV Cache）**管理机制：以 16 个 token 为一块（Block），支持 LRU 淘汰策略，不同请求可以共享部分 Block。**内存利用率提升约 60%**。

### 7. 分层内存池（EdgeMemoryManager）
这是 LiteRT-LM 最精巧的工程设计之一。将设备内存分为三层：
- **高速缓存池**（<1MB）：热点数据，延迟 <1ns，对应 L1 Cache / SRAM
- **主内存池**（8–16GB）：顺序读取的激活值，对应 DDR / LPDDR
- **存储池**（>64GB）：冷数据、备用权重，按需换入，对应 SSD / Flash

通过智能分配策略，**内存占用减少 40%，推理延迟稳定提升 2.5×，能耗降低 60%**。

### 8. 算子融合（Kernel Fusion）
传统 Attention 实现需要多次独立核函数调用（Q@K^T → Softmax → scores@V），每次调用都有 GPU 启动开销和 HBM 读写。LiteRT-LM 将整个 Attention 融合为**单次 CUDA / Metal / Vulkan 核函数调用**，HBM 读写从 4 次降至 2 次。结合 Flash Attention 2/3 实现，**长序列场景性能提升 10× 以上**。

### 9. 多语言 API
- **Kotlin API**：Android / iOS 开发，生产就绪
- **Python API**：基于 nanobind 绑定，适合快速实验
- **C++ API**：原生高性能接口，嵌入式开发首选
- **Swift API**：iOS 开发，即将发布
- **C API**：底层接口，支持更多语言绑定
- **Rust 绑定**：Rust 生态支持

### 10. 专有模型格式 + HuggingFace 直接加载
LiteRT-LM 使用 `.litertlm` 专有格式，针对推理做了深度优化。同时支持**从 HuggingFace 仓库直接加载**模型，无需手动转换，极大降低了上手门槛。

## 三、技术亮点（深度解析）

### 亮点 1：唯一支持 WebGPU 的 LLM 推理引擎

这是 LiteRT-LM 最具差异化的特性。通过 WebGPU + WASM，开发者可以直接在**浏览器**里运行 LLM，**零服务器成本、零网络延迟**。

实测数据（Chrome 134 + NVIDIA RTX 4070 Laptop GPU）：
| 模型 | 量化 | 首次推理延迟 | 持续生成速度 |
|------|------|-------------|-------------|
| Gemma-2B | INT4 | 2.3s | 42 tokens/s |
| Phi-3-mini | INT4 | 1.8s | 55 tokens/s |
| Qwen2-1.5B | INT4 | 1.1s | 78 tokens/s |

对比传统云端 API（100–500ms 延迟 + 按 Token 计费），LiteRT-LM WebGPU 方案将延迟压缩到 **<10ms**，且**完全免费**。对于需要低延迟交互的 Web AI 应用（实时翻译、代码补全、智能客服），这是一个颠覆性的能力。

### 亮点 2：与竞品的量化对比

| 特性 | **LiteRT-LM** | llama.cpp | Apple MLX |
|------|--------------|--------------|-------------|
| 全平台支持 | ✅ 全平台 | ✅ 全平台 | ❌ 仅 Apple Silicon |
| WebGPU 支持 | ✅ 原生 | ❌ | ❌ |
| KV Cache 量化 | ✅ INT8 | ❌ | ❌ |
| 分页 KV Cache | ✅ 原生 | ✅ | ✅ |
| 量化体系 | INT4/INT8/混合/GPTQ/AWQ | INT4/INT5/INT8/Q4_K/Q5_K | INT4/INT8/NF4 |
| Android 原生 SDK | ✅ | ⚠️ 需 Termux | ❌ |
| 多模态 | ✅ 通过 AI Edge Gallery | ❌ | ✅ |

与 llama.cpp 的直接性能对比（来自社区测试）：
- **CPU 解码速度**：LiteRT-LM 比 llama.cpp 快约 **3×**
- **GPU 模式**：LiteRT-LM 比 llama.cpp 快约 **7×**
- **NPU 加速**（预填充阶段）：相较 GPU 额外提升约 **3×**

### 亮点 3：三级内存池的工程价值

端侧设备的内存带宽是主要瓶颈（尤其是移动端 LPDDR5X，~68 GB/s，远远低于服务端 DDR5 的 ~400 GB/s）。LiteRT-LM 的 EdgeMemoryManager 通过三层内存池设计，最大限度地减少了跨层数据搬运：

- **热点权重**（<1MB）_pin 在 SRAM 中，零 DRAM 访问
- **激活值**（顺序读取模式）优先放在主内存池，利用预取机制
- **备用权重**（低频访问）放在存储池，按需通过 DMA 换入

这套机制在 Pixel 9 Pro（Tensor G4）上的实测效果：Gemma-4B INT4 模型推理，内存峰值占用仅 **2.8GB**，持续生成速度 **18 tokens/s**——这个表现在目前的端侧 LLM 框架里是第一梯队的。

## 五、快速上手

### 方式一：CLI 快速尝鲜（无需写代码）

```bash
# 安装 LiteRT-LM CLI
uv tool install litert-lm

# 运行 Gemma 3n 模型（自动从 HuggingFace 下载）
litert-lm run \
  --from-huggingface-repo=google/gemma-3n-E2B-it-litert-lm \
  gemma-3n-E2B-it-int4 \
  --prompt="解释一下 Transformer 架构"

# 运行带工具调用的模型
litert-lm run \
  --from-huggingface-repo=litert-community/gemma-4-E2B-it-litert-lm \
  gemma-4-E2B-it.litertlm \
  --prompt="北京今天天气怎么样？"
```

### 方式二：Android (Kotlin) 集成

```kotlin
// build.gradle
dependencies {
    implementation("com.google.ai.edge.litert:litert:0.10.1")
}

// 加载模型并推理
val model = Model.fromFile("gemma-3n-e2b-it.litertlm")

// 基本推理
val response = model.generate("法国的首都是哪里？")
println(response.text)

// GPU 加速配置
val options = LmOptions(
    runtime = Runtime.GPU,  // 使用 GPU 加速
    threads = 4
)
```

### 方式三：Python 快速实验

```bash
pip install litertlm
```


## 六、与 TensorFlow Lite 的传承关系

很多开发者会问：TensorFlow Lite 是不是被抛弃了？

答案是：**LiteRT（Lite Runtime）是 TensorFlow Lite 的直接继承者**，项目在 GitHub 上也是同一个仓库的延续（`google-ai-edge/litert`）。但 LiteRT-LM 是专门针对 LLM 推理从底层重新设计的一个子项目。

| 维度 | TensorFlow Lite | LiteRT-LM |
|------|-----------------|-------------|
| 设计目标 | CNN、RNN、小型分类/检测模型（<100MB） | **LLM 原生推理引擎** |
| 静态/动态 | 静态计算图、批量推理 | 支持动态长度序列、自回归推理 |
| KV Cache | ❌ 不支持 | ✅ 原生支持 |
| 流式生成 | ❌ | ✅ |
| 量化支持 | INT8 | INT4/INT8/混合/GPTQ/AWQ |

TensorFlow Lite 并没有"做错"什么，只是 LLM 的推理模式和它设计时的假设完全不同。LiteRT-LM 是这种认知升级后的产物。
